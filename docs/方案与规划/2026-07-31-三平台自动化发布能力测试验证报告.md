三个平台均使用工作台已有的发布排程、Node.js bridge、Python Arcs/DrissionPage runner、幂等账本和验证接口完成测试，没有使用 Codex 自带浏览器代替工作台执行发布。

能力边界：

1. 如果验收标准是“工作台能复用批准草稿，自动完成平台提交，并获得平台文章身份”，三个平台均通过。
2. 如果验收标准是“提交后立即获得公众可访问页面”，知乎和 CSDN 通过；掘金仍受平台审核与公开时延影响。
3. 平台验证码、风控、审核、账号权限和页面改版不属于工作台可完全控制的范围，必须保留人工接管与只验证不重发机制。

## 2. 测试目标与范围

### 2.1 核心目标

验证工作台是否具备以下真实能力：

```text
批准终稿
-> 创建或复用平台草稿
-> 创建发布排程
-> 登录与配置预检查
-> 自动填写平台发布设置
-> 执行正式发布
-> 查询创作后台或平台接口
-> 回写文章 ID、公开 URL 和最终状态
```

### 2.2 验收重点

1. 真实发布，不使用 mock 结果冒充平台成功。
2. 沿用同一份批准草稿，不因失败重试而创建重复草稿。
3. 相同 `scheduleId + platform + contentHash` 只能执行一条受保护的发布链路。
4. 发布动作无法确认时进入 `pending_verify`，后续只做验证，不再次点击发布。
5. 只有取得文章 ID、公开 URL或创作后台明确记录后，才能写入发布结果。
6. 公开 URL 尚不可访问时，必须使用 `published_pending_url`，不能提前标记 `published_verified`。

### 2.3 不在本轮范围

1. 微信公众号正式发布。
2. 多账号、多机器和多人并发。
3. Windows Task Scheduler 或常驻服务的长期稳定性。
4. 验证码、短信确认和平台风控的自动绕过。
5. 大批量连续发布、限流和平台封禁风险测试。

## 4. 测试方法

### 4.1 通用步骤

1. 读取批准终稿并计算 `contentHash`。
2. 为每个平台创建独立排程与幂等键。
3. 执行登录态、平台配置和载荷预检查。
4. 优先从账本恢复 `externalDraftId` 和 `editorUrl`，禁止盲目创建新草稿。
5. 打开指定草稿，填写或确认标题、正文、分类和标签。
6. 点击平台第一层发布入口和最终确认按钮。
7. 如果没有明确成功信号，停止发布动作并进入 `pending_verify`。
8. 通过创作后台记录、平台接口或公开 URL 执行只读验证。
9. 根据证据写入：
   - `published_verified`
   - `published_pending_url`
   - `pending_verify`
   - `manual_takeover_required`
   - `failed`

### 4.2 重试安全门

允许恢复同一草稿的情况仅限：

1. 发布前载荷错误，例如分类、标签或 DOM selector 不匹配。
2. 浏览器尚未进入发布动作时出现 `BrowserConnectError`。
3. 有平台 API 或创作后台证据证明原草稿仍未生成文章。

禁止自动重发的情况：

1. 最终确认已经点击，但平台结果未知。
2. 已生成文章 ID。
3. 已发现同标题创作后台记录。
4. 已进入平台审核或等待公开状态。

## 5. 分平台测试过程与结果

### 5.1 知乎

#### 测试过程

1. runner 复用已创建的知乎草稿并进入正式发布流程。
2. 第一层发布按钮已点击，但当时未找到预期的最终确认弹窗，排程进入 `pending_verify`。
3. 后续 worker 只查询创作后台，没有再次发布。
4. 前几次验证已找到同标题记录，但页面尚未提供可确认的发布或审核状态。
5. 最终从同标题创作后台记录读取到公开文章链接和文章 ID。

#### 最终结果

| 字段 | 结果 |
| --- | --- |
| Schedule 状态 | `published_verified` |
| Verify 状态 | `verified` |
| 文章 ID | `2064024161253692442` |
| 公开 URL | <https://zhuanlan.zhihu.com/p/2064024161253692442> |
| 是否重复发布 | 否 |

#### 能力判断

知乎链路完整通过。测试证明工作台可以在发布动作不确定时停止点击，通过后续创作后台验证收敛到正式文章结果。

#### 卡点

1. 发布确认弹窗结构与预期 selector 不完全一致。
2. 创作后台记录与公开状态之间存在同步延迟。
3. 知乎验证码、手机号确认或安全挑战仍需进入 `manual_takeover_required`。

### 5.2 掘金

#### 测试过程

掘金是本轮问题最多、也最能验证安全机制的平台。

1. 旧配置使用平台内部分类 ID 和标签 ID，但当前页面发布弹窗实际需要可见分类与标签名称。
2. 初始标签 `人工智能` 实际是分类，不是当前可选标签；runner 曾把分类选中态误判为标签选中态。
3. 页面存在隐藏的标签 DOM 副本，普通元素查找会命中无尺寸节点并触发 `NoRectError`。
4. 调整为：
   - 先打开发布设置弹窗；
   - 使用可见分类 `人工智能`；
   - 使用真实可选标签 `后端`；
   - 只点击可见且有实际尺寸的 `byte-select-option`；
   - 使用 `byte-select__tag` / `byte-select-option--selected` 判断选中态。
5. runner 完成最终确认后，创作后台一度找不到同标题记录，排程保持 `pending_verify`，没有盲目重发。
6. 平台草稿详情接口最终返回嵌套字段 `data.article_draft.article_id`。
7. 草稿页面按钮从“发布”变为“更新”，进一步证明平台已受理正式提交。
8. 测试结束时公开 URL 返回 404，因此最终状态被纠正为 `published_pending_url`，而不是 `published_verified`。

#### 最终结果

| 字段 | 结果 |
| --- | --- |
| Schedule 状态 | `published_pending_url` |
| Publish 状态 | `pending_review` |
| Verify 状态 | `pending` |
| 文章 ID | `7668120258260074548` |
| 预期公开 URL | <https://juejin.cn/post/7668120258260074548> |
| 测试结束时公开访问 | HTTP 404 |
| 是否重复创建草稿 | 否 |

#### 能力判断

掘金“草稿复用、表单填写、正式提交、文章 ID 获取、审核等待状态回写”已经通过；“公众可访问”尚未通过。

这不是再次发布的理由。已经生成 `article_id` 后，只允许周期性 verify，禁止重新创建草稿或再次点击发布。

#### 卡点

1. 分类、标签内部 ID 与页面可见值不是同一套输入。
2. 下拉选项存在隐藏 DOM 副本。
3. 发布设置必须先打开，分类和标签才存在。
4. `article_id` 位于 `data.article_draft.article_id`，旧 verifier 漏读嵌套字段。
5. 浏览器 runner 偶发 `BrowserConnectError`。
6. 正式提交后仍受平台审核和公开时延控制。

### 5.3 CSDN

#### 测试过程

1. 初始草稿 API 因 `X-Ca-Key is not exist` 被拒绝。

4. 创作后台找到同标题文章，并优先读取公开博客链接而不是编辑器链接。
5. 公开 URL 返回 HTTP 200，排程回写为 `published_verified`。

1. CSDN 草稿接口签名和 Header 配置必须有效。

### 6.1 已验证可用

| 分类与标签填写 | 有条件通过 | 当前三个测试平台已适配；页面改版后需要维护 |
| 正式提交 | 通过 | 三个平台均形成正式文章记录或文章 ID |

### 6.2 当前成熟度

当前能力适合：

1. 已批准终稿的单篇真实发布。
2. 低频、小批量、有人值守的渠道试运行。
3. 平台异常时由运营人员查看失败原因并人工接管。
4. `published_pending_url` 的只读复验。

当前能力不适合：

1. 无人值守的大批量连续发布。
2. 多机器同时处理同一账号。
3. 未经账号级验收就直接开启新平台。
4. 把“按钮已点击”“API 200”或“获得草稿 ID”当成正式发布成功。

## 7. 主要卡点与原因

| 优先级 | 卡点 | 底层原因 | 用户影响 | 当前处理 |
| --- | --- | --- | --- | --- |
| P0 | 平台审核与公开时延 | 外部平台异步审核，工作台无法决定放行时间 | 已提交但短时间无公开 URL | 使用 `published_pending_url`，只验证不重发 |
| P1 | 平台 DOM 变化 | 编辑器和创作后台不是稳定公开 API | selector 失效，发布前失败 | 失败关闭、诊断 DOM、按平台维护 selector |
| P1 | 隐藏 DOM 与选中态误判 | 前端组件保留隐藏下拉节点，类名不统一 | 标签看似选择，实际表单无效 | 只选择可见且有尺寸节点，校验真实选中类 |
| P1 | `BrowserConnectError` | 固定调试端口、浏览器启动时延或 profile 占用 | 预检查/验证偶发失败 | 发布前安全重试；发布后只做 verify |
| P1 | 平台配置复杂 | Cookie、CSRF、签名、分类、标签来自不同入口 | 配置错误导致草稿或发布失败 | preflight 检查，敏感配置仅存本机 |
| P2 | 本地 JSON 和单机账本 | 当前仍是单机试运行架构 | 不适合多实例并发 | 生产化前迁移数据库与分布式锁 |
| P2 | 长期运行未验证 | 尚未完成服务守护、自动拉起和持续监控 | 服务退出后排程无法自动执行 | 增加 Windows Service/Task Scheduler 和健康检查 |

## 9. 上线建议

### 9.1 可以立即执行

1. 将知乎和 CSDN 标记为“单篇受控试运行可用”。
2. 将掘金标记为“正式提交可用，公开结果需异步复验”。
3. 所有新账号先执行一篇批准测试稿验收。
4. 保持 `DIRECT_PUBLISH_MOCK=false` 与账号级 readiness 双重校验。
5. 对 `published_pending_url` 建立定时 verify，不重新执行 publish。

### 9.2 进入批量生产前必须补齐

1. runner 和 bridge 的健康检查、异常自动拉起与运行日志轮转。
2. 平台 selector 探针和页面改版告警。
3. MySQL 状态存储、并发锁和跨进程幂等。
4. 平台发布频率、账号限流与失败熔断策略。
5. 人工接管操作台和验证码/风控恢复 SOP。
6. 发布后公开 URL 的定时复验与超时告警。

## 10. 最终验收意见

本轮测试不是“所有平台都可以完全无人值守”的证明，而是确认了工作台已经具备一条真实、可追踪、失败关闭且不会盲目重发的自动发布主链路。

最终判定：

```text
知乎：完整通过
CSDN：完整通过
掘金：正式提交通过，公开验证待平台放行
综合：有条件通过，可进入单篇、低频、有人值守的真实试运行
```

后续判断自动化发布是否可以扩大规模，应以连续多次真实发布的成功率、人工接管率、平台审核耗时和 selector 失效率为依据，而不是只看一次发布成功。

## 11. 2026-08-02 Phase 1—4 全机器复测补充

本节使用工作台新增的 Publish Job、Runner、MCP Tool 和存活验证能力重新测试，结论优先于本文前面的阶段性结论。测试全程由工作台 API、bridge 和本地 Runner 执行，没有使用 Codex 浏览器代替发布动作，也没有把人工确认作为链路组成部分。

### 11.1 环境与底层链路

- Windows 本地工作台：`http://127.0.0.1:3047`。
- 本地 bridge：`127.0.0.1:9528`；Arcs/DrissionPage Runner：`127.0.0.1:9530`。
- 三个平台使用独立持久浏览器 profile；登录凭证不进入 Tool 参数、日志或项目文件。
- Runner 增加跨进程单实例锁、分平台串行锁、首次浏览器连接自动重试和页面加载超时。

- MCP Server 使用官方 SDK，把 `publish_job_create/run/get/reconcile`、认证探测、预检和存活检查映射为高层 Tool；MCP 本身不操作网页，也不保存第二套发布状态。

### 11.2 真实复测结果

### 11.3 能力判断

- CSDN、知乎：已经具备单篇、低频的全机器发布与 URL 回填能力，但只有完成 24/72 小时连续存活观测后才能称为稳定发布能力。
- 掘金：提交 Tool 可用，稳定发布能力不成立。平台接受请求和返回文章 ID 仍可能被风控撤销、删除或不公开。
- 三平台统一能力：幂等任务、账号串行、发布后只读 reconciliation、URL 生命周期和 MCP/REST 同源状态已经成立。
- MCP 的作用是标准化 Agent 对工作台高层能力的发现和调用；实际登录会话、页面执行、风控识别和 URL 核验由 Runner/bridge 完成。把浏览器动作封装为 MCP Tool 不会降低平台风控。

### 11.4 当前卡点与下一判定点

1. 掘金是当前唯一 P0 卡点。可行路径不是继续更换自动化框架，而是保留真实浏览器页面上下文、加强平台专属技术内容准入、低频串行提交，并把“公开后持续存活”作为唯一成功标准。
2. CSDN、知乎当前仅为 `public_observed`，尚无 24/72 小时样本，不能提前写成 `stable_published`。
3. CAPTCHA、手机号确认和安全挑战不应自动绕过；无人值守模式下必须熔断该账号写队列，等待登录态在外部恢复后由机器探针自动续跑。
4. 当前本地 JSON 账本适合单机验证；多机生产需迁移数据库和分布式租约。
