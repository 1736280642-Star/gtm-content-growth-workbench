# 自动化机器发布链路能力与测试结果

## 1. 结论

当前系统已经达到**可运行、可观察、可幂等恢复、可自动回填 URL、可按 24h/72h 复验的单篇低频机器发布能力**。CSDN 与知乎已完成真实正式发布、公开页确认和 URL 回填；掘金完成了平台提交并获得文章 ID，但后续公开核验持续失败，因此不能算稳定发布成功。

工程能力可以进入受控试运行，但三平台整体仍不满足无人值守批量扩量条件。可靠性接口当前应保持 `rolloutReady: false`：原因不是链路无法执行，而是不同终稿样本数量、24h/72h 自然存活证据和掘金公开转换率尚未达到门槛。

## 2. 测试目标与边界

本次验证回答四个问题：

1. 机器能否从既有终稿创建并执行唯一的 Publish Job。
2. 平台接受发布后，系统能否通过创作后台或公开页获得真实文章 ID 与 URL。
3. 暂未公开、被删除或平台风控时，系统能否停止误报和重复提交。
4. 公开文章能否进入 24h/72h 存活验证，并为扩量决策提供可靠指标。

发布动作只使用工作台现有 API、Bridge、Runner 和 Worker。MCP 仅提供高层 Tool 入口，不直接操作网页，也不保存第二套状态。测试不以按钮点击、HTTP 200 或返回文章 ID 单独作为发布成功证据。

## 3. 测试环境

| 层级 | 环境/组件 | 作用 |
| --- | --- | --- |
| 控制面 | Windows 本地 Workbench，Next.js API | 终稿准入、Publish Job、状态和可靠性指标 |
| 调度面 | `workers/direct-publish-worker.mjs` | 扫描到期发布与到期 reconciliation |
| 桥接层 | loopback Bridge `127.0.0.1:9528` | 统一平台适配入口和请求边界 |
| 执行层 | Arcs/DrissionPage Runner `127.0.0.1:9530` | 使用已登录 Chromium 页面上下文执行平台动作 |
| 会话层 | CSDN、掘金、知乎独立持久 profile | 隔离登录态、避免跨平台和日常浏览器污染 |
| 工具层 | 官方 MCP SDK Server | 暴露 Publish Job 高层 Tool，异步返回 durable handle |
| 状态层 | 本地 JSON 与幂等账本 | 单机试运行持久化，不等同于多实例生产数据库 |

测试期间未把 Cookie、Token、完整响应正文或 profile 数据写入报告、Tool 返回值和 Git。

## 4. 已实现链路

```text
已确认终稿
  -> 平台 preflight 与风险门禁
  -> 创建唯一 Publish Job
  -> Worker 异步领取
  -> Bridge / Runner 串行执行
  -> 平台受理或明确失败
  -> 只读 reconciliation
  -> 创作后台/公开 URL 证据
  -> URL 回填
  -> 24h/72h 存活验证
  -> 可靠性指标与扩量判断
```

关键实现包括：

- `scheduleId + platform + contentHash` 幂等键和跨进程单实例/分平台串行锁。
- 发布与 reconciliation 长任务异步入队，MCP/REST 立即返回同一个 Job handle。
- 三平台响应和可见 Toast 的脱敏捕获；最终状态仍以后台或公开 URL 为准。
- `public_observed`、`stable_published`、`removed_after_publish` 等生命周期语义。
- 每个平台独立保存文章 ID、URL、状态和错误，避免多平台结果互相覆盖。
- 公开实体按平台文章 ID 或规范化 URL 去重，多个历史 Job 不冒充多个公开样本。
- 平台级认证/风险写门禁；不确定结果只做只读核验，不自动重复发布。
- 24h/72h 精确里程碑、分段退避、公开任务优先级和可靠性 API。

## 8. 云端常驻生产路径

最简可落地方案不是重写为 Serverless，而是把现有组件原样放到一台受控的单实例云执行节点：

1. Workbench API、Bridge、Arcs Runner、Chromium 和平台 profile 同机部署。
2. Workbench、Bridge、Runner 作为常驻服务并在异常退出后自动重启。
3. 云定时器每分钟执行一次 `worker:direct-publish -- --once`；禁止并发触发。
4. Worker 通过 loopback Workbench API 执行到期扫描；24h/72h 规则仍由 `nextVerificationAt` 决定。
5. 公网只开放经过认证的前台 HTTPS；Bridge/Runner 端口保持 loopback。
6. 浏览器 profile 位于加密持久磁盘，Token 由密钥管理注入，日志不输出凭证。
7. 前台只负责配置、展示结果和异常处理，关闭前台页面不影响后台执行。

当前 JSON 状态和本机账本决定了“原样部署”只能是单实例。多实例之前必须先迁移数据库、分布式租约和幂等账本；不能直接复制云主机横向扩容。详细启动、恢复、网络和验收要求见 [`P0-自动化发布能力与渠道配置说明书.md`](./P0-自动化发布能力与渠道配置说明书.md)。

## 9. 卡点与风险

1. **掘金平台风控**：提交接受后仍可能不公开或被删除，是当前最大业务风险。
2. **样本不足**：每个平台尚未达到至少 3 个不同 `draftId` 的真实已受理样本。
3. **自然时间不足**：24h/72h 存活率不能由单元测试或短时复验替代。
4. **单机持久化**：本地 JSON 适合单实例试运行，不支持跨实例一致性与自动故障转移。
5. **页面变化**：平台编辑器、选择器和安全策略改版会造成适配器失效。
6. **账号与出口环境**：云迁移改变设备指纹或出口 IP，必须重新做三平台账号级 dry-run 和单篇验收。
7. **认证挑战**：验证码、手机确认和安全挑战不能自动绕过；无人值守模式必须熔断写队列。

## 10. 扩量标准与下一步

三平台只有同时满足以下门槛，才能把 `rolloutReady` 调整为 `true`：

- 每个平台至少 3 个来自不同 `draftId` 的真实已受理样本。
- 提交接受率和公开转换率均不低于 90%。
- 24h 与 72h 存活率均不低于 95%。
- 风险阻断率不高于 10%。
- 真实重复发布数为 0。

推荐顺序：先完成单实例云执行节点和重启恢复验收，再积累 CSDN/知乎不同终稿样本；掘金保持低频、严格内容准入和只读存活观察。任何平台未达到公开与存活标准时，都不应通过降低指标门槛来换取“通过”。
