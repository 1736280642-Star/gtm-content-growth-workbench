# GEO 托管邮件与安全链接配置指南

## 结论

GEO 托管模式要把策略确认、代表样文确认、异常处理和每日公开 URL 汇总真正发送到用户邮箱，部署环境必须补齐四项配置：

| 配置项 | 是否必需 | 值从哪里来 | 作用 |
| --- | --- | --- | --- |
| `HOSTED_PUBLIC_BASE_URL` | 外部邮件必需 | 工作台对用户开放的 HTTPS 域名 | 生成用户可以访问的确认和结果链接 |
| `HOSTED_REVIEW_LINK_SECRET` | 生产环境必需 | 部署人员在本机随机生成 | 对托管行动链接进行服务端签名 |
| `HOSTED_EMAIL_DELIVERY_URL` | 真实投递必需 | 企业邮件 API，或自行部署的邮件适配器 | 接收工作台的邮件投递请求 |
| `HOSTED_EMAIL_DELIVERY_TOKEN` | 真实投递必需 | 邮件 API 提供，或为自建适配器随机生成 | 工作台与邮件投递接口之间的 Bearer 鉴权 |

缺少任一邮件投递配置时，通知 Outbox 保持 `pending_config` 或可重试状态，不得把任务标记为已发送。`http://127.0.0.1:3027` 只适合本机验收，不能作为发给外部用户的邮件链接。

## 1. 配置内容

Docker 3027 生产部署把以下字段写入本机、被 Git 忽略的 `.env`。本地非 Docker 开发可以把同名字段写入 `.env.local`。仓库中的 `.env.example` 只保留空值和格式示例。

```dotenv
HOSTED_PUBLIC_BASE_URL=https://workbench.example.com
HOSTED_REVIEW_LINK_SECRET=<本机生成的随机值>
HOSTED_EMAIL_DELIVERY_URL=https://mail-relay.example.com/send
HOSTED_EMAIL_DELIVERY_TOKEN=<邮件接口提供或本机生成的随机值>
```

要求：

- `HOSTED_PUBLIC_BASE_URL` 使用用户实际可以访问的 HTTPS Origin，不填写 `127.0.0.1`、`localhost`、管理后台内网地址或邮件接口地址；结尾斜杠会被程序移除。
- `HOSTED_REVIEW_LINK_SECRET` 使用独立随机值，不得复用数据库密码、模型 API Key、渠道 Cookie 或邮件 Token。
- `HOSTED_EMAIL_DELIVERY_URL` 必须能从 `workbench-web` 和托管 Worker 所在容器访问。宿主机适配器使用 `http://host.docker.internal:<port>/send`，外部服务优先使用 HTTPS。
- `HOSTED_EMAIL_DELIVERY_TOKEN` 是工作台访问投递接口的服务端凭据。只有当供应商原生接口完全符合下述请求契约时，才可以直接使用供应商 Token；通常应由邮件适配器使用独立 Token，再把供应商 API Key 保存在适配器侧。

## 2. 生成两个随机值

在部署机器的 PowerShell 中分别执行。命令只在当前终端显示结果；生成后立即保存到本机秘密配置，不要粘贴到聊天、Issue、日志或 Git 提交。

生成链接签名密钥：

```powershell
node -e "process.stdout.write(require('node:crypto').randomBytes(48).toString('base64url'))"
```

生成自建邮件适配器的 Bearer Token：

```powershell
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"
```

如果企业邮件 API 已经提供服务端 Bearer Token，`HOSTED_EMAIL_DELIVERY_TOKEN` 使用企业提供的值，不再额外生成。不要使用邮箱登录密码。

## 3. 邮件投递接口契约

当前工作台不直接连接 SMTP，也不假设某一家邮件供应商。`HOSTED_EMAIL_DELIVERY_URL` 指向一个受保护的 HTTP `POST` 接口：

```http
POST /send
Authorization: Bearer <HOSTED_EMAIL_DELIVERY_TOKEN>
Content-Type: application/json
x-idempotency-key: <通知任务ID>
```

请求体：

```json
{
  "to": "user@example.com",
  "subject": "邮件标题",
  "text": "纯文本正文",
  "html": "<p>HTML 正文</p>"
}
```

成功响应返回 HTTP 2xx，并建议提供供应商消息 ID：

```json
{
  "messageId": "provider-message-id"
}
```

也可以返回 `id`。没有消息 ID 时工作台会记录 `accepted`，但生产适配器应保留供应商回执，方便定位退信和重复投递。

邮件适配器负责补充供应商要求的发件人、已验证域名和供应商 API Key，并完成以下检查：

1. 使用常量时间比较验证 Bearer Token；
2. 使用 `x-idempotency-key` 防止同一通知重复发送；
3. 仅接受合法邮箱、标题、文本和 HTML 字段，限制请求体大小；
4. 不在日志中记录 Token、完整邮件正文或用户隐私；
5. 把供应商拒绝、超时和限流转换为非 2xx，交给工作台按策略重试。

## 4. Docker 3027 配置与重启

首次部署时从公开模板创建本机配置；已有 `.env` 时只补充上述四项，不要覆盖现有数据库密码和其他配置。

```powershell
Copy-Item .env.example .env
```

人工填写 `.env` 后重新构建和部署：

```powershell
npm.cmd run docker:3027:deploy -- -NoOpen
```

只检查四个变量是否进入 Web 容器，不打印实际值：

```powershell
docker compose exec -T workbench-web node -e 'for (const key of ["HOSTED_PUBLIC_BASE_URL","HOSTED_REVIEW_LINK_SECRET","HOSTED_EMAIL_DELIVERY_URL","HOSTED_EMAIL_DELIVERY_TOKEN"]) console.log(`${key}=${process.env[key]?.trim()?"SET":"UNSET"}`)'
```

验收标准：

1. 四项检查均为 `SET`；
2. `HOSTED_PUBLIC_BASE_URL` 从外部网络可以打开工作台对应页面；
3. 邮件适配器健康，并且容器可以访问 `HOSTED_EMAIL_DELIVERY_URL`；
4. 触发一条测试通知后，邮件供应商返回消息 ID，Outbox 从待处理进入 `sent`；
5. 邮件中的确认链接可以在无工作台登录会话的浏览器中打开，并且篡改 Token 后被拒绝；
6. 重复处理同一 Outbox 任务不会发送第二封邮件。

## 5. 安全、轮换与故障影响

- `.env`、`.env.local`、真实域名内网路径、Token、API Key、Cookie、邮箱密码均不得提交 GitHub。
- 轮换 `HOSTED_REVIEW_LINK_SECRET` 会让使用旧签名生成的未完成行动链接失效，应先确认待处理链接范围，再安排轮换和补发。
- 轮换 `HOSTED_EMAIL_DELIVERY_TOKEN` 时，先更新邮件适配器，再更新工作台并重启，避免通知在切换窗口持续失败。
- 邮件供应商 API Key 只保存在邮件适配器或秘密管理服务中，不进入工作台数据库和前端页面。
- 邮件服务暂时不可用时，工作台保留 Outbox 和失败原因；用户影响是通知延迟，不应绕过确认门禁继续正式发布。

## 6. 最简落地路径

如果已经有企业邮件 API，直接让它满足上述接口契约，是成本最低的路径。如果只有供应商 SMTP 或专有 REST API，则部署一个轻量邮件适配器，把供应商差异、发件人和退信处理封装在适配器内部。工作台继续只依赖稳定的四项配置，后续更换供应商不需要修改托管业务代码。
