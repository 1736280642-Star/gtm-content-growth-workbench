# P0 自动化发布能力与渠道配置说明书

## 1. 文档结论

当前 P0 已完成“正式发布排程、状态治理、三平台浏览器执行器和持续存活验证”。CSDN、知乎已经完成真实发布、公开核验和 URL 回填；掘金已被平台接受提交，但公开核验失败，不能判定稳定发布。当前适合受控的单篇、低频试运行，尚未达到无人值守批量扩量门槛。

2026-08-04 更新：3027 已增加 `/publishing` 发布控制塔；月度生产与自由生产统一进入 `Publish Job -> Worker -> reconciliation -> URL 自动回填 -> 24h/72h -> reliability`。前台不直接执行平台动作，部署时必须同时运行常驻 Worker。完整接线见 [`2026-08-04-3027自动发布前台接入说明.md`](./2026-08-04-3027自动发布前台接入说明.md)。

已经具备：

```text
已确认终稿
-> 创建平台发布排程
-> 到期执行
-> 登录与配置预检查
-> 载荷校验
-> 发布 attempt 记录
-> 发布/验证状态记录
-> reconciliation 自动回填公开 URL
-> 24h/72h 存活验证与 reliability
-> 失败原因和下一步记录
```

已经补齐：

1. 微信公众号 `draft/add -> freepublish/submit -> freepublish/get` 正式发布与状态轮询。
2. CSDN、掘金、知乎的 Arcs/DrissionPage 本地浏览器执行器、持久 profile 和发布后验证。
3. 知乎验证码、手机确认和安全挑战的失败关闭状态；系统不自动绕过平台安全机制。
4. `scheduleId + platform + contentHash` 幂等键、bridge/runner 双层重复保护。
5. 到期扫描自动处理 `pending_verify`；待验证任务只查询状态，不重复发布。
6. 公开 URL 自动回填、24h/72h 精确存活调度、删除后状态和平台可靠性指标。
7. Publish Job REST API 与 MCP Tool 共用同一状态，长任务由确定性 Worker 异步执行。

仍需现场完成：

1. CSDN、知乎的 24h/72h 自然存活样本和每平台至少 3 个不同终稿样本。
2. 掘金公开存活率与平台风控仍未达标。
3. 云端单实例执行节点、进程守护、定时触发和监控告警的系统级部署。
4. 平台页面改版后的 selector 维护。

因此，mock 中出现 `published_pending_url` 仍只证明状态机正确；真实模式只有官方状态或平台公开页/创作中心验证通过，才会写入正式发布结果。

## 2. 当前自动化发布能力

### 2.1 使用的技术与工具

| 能力 | 当前技术/工具 | 当前状态 | 用户影响 |
| --- | --- | --- | --- |
| 工作台与 API | Next.js 15、TypeScript、Route Handlers | 已实现 | 页面和外部任务可以创建、查询、dispatch 发布任务 |
| 状态持久化 | 本地 JSON `data/workbench-state.json` | 已实现，单机试运行 | 可记录 schedule、attempt、失败和 URL；不适合多人并发生产 |
| 平台适配合同 | TypeScript `PublishAdapter` | 已实现 | 四个平台共用 `checkAuth/validatePayload/publish/verify` 合同 |
| 定时排程 | `scheduledAt` + 常驻 Worker | 已实现 | Worker 到期领取；正式部署必须保持 Worker 常驻 |
| 重复保护 | `scheduleId + platform + contentHash` + 本机持久账本 | 已实现 | 相同任务重复请求不会再次点击发布 |
| 微信正式发布 | Node.js 本机 bridge + 微信官方发布 API | 已实现 | 创建草稿、提交发布、轮询状态并回写任务 ID/文章 ID/URL |
| 掘金/CSDN/知乎草稿 | Node.js bridge + Cookie/内部写作接口 | 实验性草稿能力 | 平台接口易变化，不应作为长期正式发布主路径 |
| 正式发布 mock | 本地 mock adapter | 已实现 | 用于验证状态机，不写入外部平台 |
| 浏览器正式发布 | Arcs/DrissionPage 本机 runner + 分平台 profile | 已实现执行器 | CSDN、掘金、知乎可正式点击发布；仍需账号现场验收 |
| 发布验证 | 微信官方查询 + 管理后台/公开页验证 | 已实现 | 不会把“点击按钮/API 200”直接当成正式发布成功 |
| 风控熔断 | `risk_blocked` / `auth_expired` | 已实现状态合同 | 验证码、登录失效或风控出现时停止写入，不伪造成功 |

### 2.2 核心接口

```text
GET  /api/publish-schedules
POST /api/publish-schedules
POST /api/publish-schedules/[id]/run
POST /api/publish-schedules/[id]/verify
POST /api/direct-publish
GET  /api/publish-jobs
POST /api/publish-jobs
POST /api/publish-jobs/[id]/dispatch
POST /api/publish-jobs/[id]/reconcile-dispatch
GET  /api/publish-reliability
```

创建排程的最小输入：

```json
{
  "publishRecordId": "pub-xxx",
  "platforms": ["wechat", "juejin", "csdn", "zhihu"],
  "scheduledAt": "2026-07-14T10:00:00.000Z",
  "matrixItemId": "monthly-matrix-item-id"
}
```

进入正式发布的终稿必须满足：

1. 稿件状态为 `final`。
2. 终稿质检通过。
3. `distributionAllowed` 不为 `false`。
4. 标题非空。
5. Markdown 正文长度不少于 80 个字符。
6. 发布时间是有效时间。

### 2.3 状态解释

| 状态 | 业务含义 |
| --- | --- |
| `scheduled` | 等待到期执行 |
| `pending_config` | 缺少平台配置或发布能力 |
| `precheck_failed` | 登录态、载荷或平台参数预检查失败 |
| `publishing` | 平台适配器正在执行 |
| `published_verified` | 已确认正式发布，并获得可验证结果 |
| `published_pending_url` | 已确认正式发布，公开 URL 等待后续回填 |
| `pending_verify` | 发布动作已完成，平台仍在审核或等待验证 |
| `manual_takeover_required` | 验证码、手机确认或安全挑战需要人工处理 |
| `failed` | 发布或验证失败 |

## 3. 本地配置规则

### 3.1 配置文件

敏感字段只允许写入项目根目录的本机文件：

```text
.env.local
```

该文件已被 `.gitignore` 忽略。禁止把以下内容写入本文档、Git、聊天记录或截图：

1. AppSecret。
2. Cookie。
3. Access Token、CSRF/XSRF Token。
4. 完整请求 Headers。
5. 浏览器 profile 文件。
6. 私有账号 URL、手机号或账号标识。

### 3.2 模式开关

```dotenv
# 默认不配置时使用 mock，只验证状态机，不写入外部平台
DIRECT_PUBLISH_MOCK=true

# 真实适配器完成并经过 dry-run 验收后才允许开启
DIRECT_PUBLISH_ENABLED=true

# bridge 和 Arcs runner 必须使用同一份本机令牌
WECHATSYNC_BRIDGE_TOKEN=
WECHATSYNC_BRIDGE_URL=http://127.0.0.1:9528
ARCS_RUNNER_URL=http://127.0.0.1:9530
```

真实 `publish()` 已实现，但不应仅通过开启 `DIRECT_PUBLISH_ENABLED` 判断账号验收完成。未配置 bridge token、非本机 URL、登录失效或平台权限不足都会失败关闭。

### 4.1 推荐技术路径


### 4.3 获取与验收步骤

1. 使用已认证、具备内容发布能力的公众号账号登录管理后台。
2. 在基本配置页面获取 AppID，并生成/重置 AppSecret。
3. 确认调用机器的公网出口 IP，将其加入白名单。
4. 在素材库上传测试封面，取得永久素材 `media_id`。
5. 先验证 access token 获取，不创建文章。
6. 再创建一篇 Kari 已批准的测试草稿。
7. 人工确认草稿内容、封面和排版无误。
8. 调用 `freepublish/submit`，记录返回的发布任务 ID。
9. 轮询 `freepublish/get`，只有平台确认成功才进入 `published_verified` 或 `published_pending_url`。
10. 权限不足、IP 白名单错误或账号不支持发布时记录 `pending_config`，不伪造成功。

## 8. 浏览器 profile 安全规则

### 8.1 托管用户的正式授权入口

托管用户统一从 `/hosted/connect/[channel]?orderId=...` 完成授权。正式交互只包含：打开专用登录窗口、本人完成登录、确认账号用于当前产品。下文的 Cookie、CSRF、Headers、Gateway Key 等字段仅用于运营人员维护旧 Bridge 或诊断兼容链路，不得制作成托管用户表单，也不得要求用户通过聊天、邮件或文档传递。

掘金、CSDN、知乎的 profile 应放在项目目录之外，例如：

```text
%LOCALAPPDATA%/JotoPublishProfiles/juejin
%LOCALAPPDATA%/JotoPublishProfiles/csdn
%LOCALAPPDATA%/JotoPublishProfiles/zhihu
```

原因：浏览器 profile 内含 Cookie、Local Storage 和账号会话，属于敏感凭证。放在项目外可以降低被 Git、压缩包或同步软件误上传的风险。

后续代码建议增加以下“路径字段”，字段值只写入 `.env.local`：

```dotenv
JUEJIN_BROWSER_PROFILE_DIR=
CSDN_BROWSER_PROFILE_DIR=
ZHIHU_BROWSER_PROFILE_DIR=
```

## 9. 系统级定时任务

`scheduledAt` 负责记录计划时间；`POST /api/direct-publish` 每次扫描会先轮询 `pending_verify`，再执行到期 `scheduled` 任务。仓库已提供常驻 `direct-publish-worker`，仍需由本机服务管理器或部署环境负责启动和守护进程。

推荐本地 P0：

```powershell
npm.cmd run worker:direct-publish -- --base-url http://127.0.0.1:3000 --interval-seconds 30
```

生产环境可以换成常驻队列，但 P0 不需要先引入大型队列系统。

定时 Worker 必须满足：

1. 同一 schedule 不并发执行。
2. 已确认发布不重复执行。
3. 失败保留 retryCount、failureReason 和 nextAction。
4. 人工接管状态不会被自动重试覆盖。
5. 进程退出或机器重启后可以继续扫描未完成排程。

### 9.1 云端常驻部署结论

现有链路不适合直接放入无状态 Serverless：三平台正式发布依赖 Chromium、持久 profile、稳定出口网络和本地 loopback 调用。最低成本且无需重写 Runner/Worker 的生产化路径，是部署一台**单实例云执行节点**。推荐优先使用与真实测试环境一致的 Windows 云主机；其他系统必须先完成 DrissionPage、Chromium 和字体/窗口环境的等价验收。

```text
用户浏览器
  -> HTTPS 反向代理
  -> Workbench 前台与 Publish Job API

云执行节点内部（同一主机）
  Cloud Scheduler / Task Scheduler
    -> direct-publish-worker --once
    -> Workbench loopback API
    -> Wechatsync Bridge 127.0.0.1:9528
    -> Arcs Runner 127.0.0.1:9530
    -> Chromium + 分平台持久 profile
    -> 平台发布/只读核验
    -> 状态、公开 URL、24h/72h 证据回写
```

前台只承担以下职责：

1. 配置已经批准的终稿和排程。
2. 展示 Job、平台状态、公开 URL、存活里程碑和可靠性指标。
3. 展示风险熔断、认证失效和明确的异常处理建议。

前台页面不承担定时触发，也不应成为 Worker 的存活条件。关闭页面后，云端执行节点仍应继续扫描和核验。

### 9.2 需要常驻的进程

| 组件 | 启动入口 | 部署要求 |
| --- | --- | --- |
| Workbench | 项目现有 Next.js 生产启动方式 | 单实例、持久工作目录；只向反向代理开放必要页面/API |
| Bridge | `npm.cmd run bridge:wechatsync` | 与 Runner、Workbench 同机；只监听 `127.0.0.1:9528` |
| Arcs Runner | `npm.cmd run arcs:runner:start` | 与浏览器 profile 同机；只监听 `127.0.0.1:9530` |
| Chromium | `ARCS_BROWSER_PATH` 指向的浏览器 | 固定版本策略、持久磁盘、三个相互隔离的 profile |
| Worker | `npm.cmd run worker:direct-publish` | 常驻循环或由云定时器执行 `--once`，二选一 |

推荐云端采用“常驻 Workbench/Bridge/Runner + 定时单轮 Worker”：

```powershell
npm.cmd run worker:direct-publish -- --base-url http://127.0.0.1:3000 --once --limit 20
```

云调度器每分钟触发一次，并设置 `concurrencyPolicy=Forbid` 或等价的“上一轮未结束则不启动下一轮”。不要同时启动常驻循环 Worker 和定时单轮 Worker，避免无收益的重复扫描。发布存活的 24h/72h 时间点由工作台状态中的 `nextVerificationAt` 决定，云调度器只负责唤醒，不复制业务规则。

### 9.3 启动、健康检查与恢复顺序

1. 挂载持久磁盘并注入运行时配置。
2. 启动 Workbench，确认 loopback 健康检查通过。
3. 启动 Arcs Runner 与 Bridge，只检查就绪状态，不执行发布。
4. 启用云定时器；Worker 先执行到期只读 reconciliation，再领取到期的新发布任务。
5. 进程异常退出时由系统服务自动重启；机器重启后仍按上述顺序恢复。

健康检查只能返回组件是否就绪、队列积压和最近扫描时间，不得返回 Token、Cookie、完整响应正文或 profile 内容。云主机失联后，排程和 `nextVerificationAt` 不应丢失；恢复后 Worker 会补扫到期任务，但实际核验时间会晚于目标里程碑，因此必须记录调度延迟。

### 9.4 网络与安全边界

1. 公网只开放 HTTPS 反向代理；`9528`、`9530` 和内部 Workbench 端口不得公开。
2. Runner 与 Bridge 共用的令牌由云密钥管理或主机级安全配置注入，不写入镜像、仓库和日志。
3. 浏览器 profile 放在加密持久磁盘，按平台隔离，不使用个人日常浏览器 profile。
4. 管理入口必须补身份认证、最小权限和审计；发布 API 不允许匿名公网调用。
5. 使用稳定区域和稳定出口 IP；不要跨区域频繁更换 IP 或复制同一账号 profile 到多台机器并发运行。
6. 备份只包含可恢复的业务状态；包含账号会话的 profile 备份必须按敏感凭证管理。

### 9.5 单实例限制与后续升级

“原样部署”阶段必须保持单实例，因为当前 `data/workbench-state.json` 和本机幂等账本适合单机，不提供跨主机事务、分布式租约和主从切换。持久磁盘能解决重启后的状态恢复，但不能解决多实例并发写。

只有出现多账号并行、跨区容灾或明显吞吐瓶颈后，再把 Publish Job、Attempt、平台门禁和幂等账本迁移到数据库/队列，并增加租约与 fencing token。迁移前不得通过复制云主机横向扩容浏览器执行器。

### 9.6 云端验收门槛

- 主机重启后四个组件自动恢复，未完成 Job 不丢失、不重复发布。
- 连续 72 小时调度无漏扫，扫描延迟和进程重启可观测。
- 相同幂等键的真实重复发布数为 0。
- CSDN、知乎能够继续完成 URL 回填与 24h/72h 只读核验。
- 掘金未公开或被删除时保持失败/待核验语义，不冒充成功、不自动重发。
- 前台关闭时后台链路继续运行；Runner/Bridge 端口从公网不可访问。
- 日志、镜像、状态接口和备份不包含 Token、Cookie、手机号或 profile 数据。

## 10. 推荐真实接入顺序

### 阶段一：微信官方 API

1. 只做配置诊断和 access token 检查。
2. 创建批准的测试草稿。
3. 实现正式发布和状态轮询。
4. 验证 URL、文章 ID 和失败记录。

### 阶段二：三平台浏览器 dry-run

1. 安装并启动 `arcs-runner` 的 DrissionPage 环境。
2. 分平台建立持久 profile。
3. 只验证登录、编辑器、分类/标签和内容填写。
4. 不点击发布。

### 阶段三：单平台正式发布

按 `CSDN -> 掘金 -> 知乎` 顺序，每次只开放一个平台，并使用单篇批准测试稿。

### 阶段四：定时发布

四平台单次真实发布全部通过后，启动并守护 `worker:direct-publish`。不要在单次发布尚未稳定时直接开放批量定时任务。

## 11. P0 验收清单

每个平台至少完成一次以下闭环：

- [ ] 配置预检查能区分 `ready`、`pending_config`、`auth_required`。
- [ ] dry-run 不写入或发布外部内容。
- [ ] 只发布 Kari 批准的测试稿。
- [ ] 记录平台、schedule ID、attempt ID 和执行时间。
- [ ] 正式发布后通过管理后台或公开页验证。
- [ ] 记录真实平台文章 ID；未知时保持为空。
- [ ] 自动获得 URL 时记录 URL；否则设置 `pendingCsvReturn`。
- [ ] 失败时记录业务可读原因和下一步。
- [ ] 验证码、手机确认、安全挑战进入人工接管。
- [ ] 重试不会生成重复文章。
- [ ] 日志和提交中不存在密钥、Cookie、Token、手机号或私有链接。

## 12. 长期维护判断

1. 微信优先维护官方 API，避免浏览器自动化。
2. 掘金、CSDN、知乎优先维护浏览器 profile 和页面操作合同，Cookie/内部接口只作为诊断兜底。
3. 平台选择器、分类和标签映射应独立配置，不写死在业务页面。
4. 同一类平台变化连续出现三次后，应把修复沉淀成 adapter 测试、诊断脚本和故障 SOP。
5. 月度矩阵只依赖统一发布合同，不直接依赖平台页面实现，避免平台变化导致主业务重构。
