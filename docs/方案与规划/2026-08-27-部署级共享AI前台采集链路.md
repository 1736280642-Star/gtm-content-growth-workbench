# 部署级共享 AI 前台采集链路

## 结论

AI 前台采集采用“一个部署级执行池服务多个托管用户”的模式。Chrome 扩展、Windows 采集伴侣和 AI 测试账号只存在于部署人员维护的 24 小时 Windows 电脑；普通用户只登录工作台、选择产品与平台、发送请求。

## 实现逻辑

1. 部署人员使用 `HOSTED_CAPTURE_SETUP_TOKEN` 进入首页部署控制台，生成一次性部署配对码。
2. Windows 采集伴侣用配对码登记为 `deployment_shared` 设备；此设备随后登记的 AI 账号连接自动继承相同执行范围。
3. 普通用户发送请求时不提交 `deviceId` 或 `connectionId`。服务端根据平台、在线状态和排队长度选择共享连接。
4. 每个任务同时写入 `requested_workspace_id` 和 `requested_user_id`。状态查询必须匹配当前登录身份，避免跨工作区读取。
5. 伴侣继续轮询自己设备下的队列，并串行驱动 Chrome 扩展完成页面操作和证据上传。

## 为什么要这样改

原链路把设备和 AI 账号绑定到普通用户工作区，意味着每个用户都要安装扩展、启动伴侣、配对电脑并维护登录状态。这与“租用统一 24 小时服务器”的产品模式冲突，也会把部署复杂度和故障处理转嫁给普通用户。

共享执行范围解决设备归属问题，请求归属字段解决多租户结果隔离问题。两者缺一不可：只共享设备会丢失用户边界，只记录用户而不共享执行器仍会要求用户装工具。

## 部署人员步骤

1. 执行数据库迁移 `20260827_042_v5_deployment_shared_ai_capture.sql`。
2. 生成至少 32 字节随机值，写入 Vercel 的 `HOSTED_CAPTURE_SETUP_TOKEN`，然后重新部署。
3. 在常开 Windows 电脑加载 `browser-extension`，把扩展 ID 写入本机 `V5_CAPTURE_EXTENSION_ID`。
4. 把正式 HTTPS 工作台地址写入本机 `V5_WORKBENCH_BASE_URL`；需要独立 Chrome 档案时再设置 `V5_CAPTURE_CHROME_PROFILE_DIRECTORY`。
5. 首页切换“我是部署人员”，在共享采集服务器板块生成部署配对码。
6. 运行 `npm.cmd run capture-companion:start`，在扩展中输入配对码；只在这台电脑登录专用中立 AI 测试账号。
7. 检查设备和账号在线后运行 `npm.cmd run capture-companion:autostart`。

## 普通用户步骤

1. 用工作邮箱登录并完成产品资料与委托。
2. 在“是否开启 AI 前台测试？”选择“是，发送请求”。
3. 确认共享服务器在线，选择平台并发送。
4. 之后只查看任务状态；不安装扩展、不生成配对码、不填写 Setup Token、Cookie 或账号密码。

## 用户影响与维护边界

- 用户端操作从“安装与绑定”缩减为“选择与发送”。
- 服务器离线、AI 登录失效和扩展适配问题统一由部署人员处理。
- 迁移前生成的个人设备仍标记为 `user_private`，不会被新的托管请求自动选中。
- 当前执行器按单机串行运行；请求增多时可增加多台 `deployment_shared` 设备，服务端会优先选择在线且队列更短的连接。
