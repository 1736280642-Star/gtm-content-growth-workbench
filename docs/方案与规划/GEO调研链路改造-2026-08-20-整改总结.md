# GEO 调研链路一致性整改总结

> 整改日期：2026-08-20
> 对齐范围：2026-08-19 至 2026-08-20 的 GEO 方案/总结、2026-08-19 提交代码、官网审计与发布批次闭环
> 目标：消除“文档已闭环、代码实际未闭环”的完整性缺口，并让失败在正式写入前暴露

## 一、整改结论

本次整改没有扩展新的产品阶段，而是收紧现有 P0–P3 的事实链。整改后的主路径为：

```text
真实前台观测 → 基线 → 人工批准蓝图 → 内容发布
→ 发布存活与 AI 样本批次闭合 → 单任务复测 → 与绑定基线计算 delta
→ 优先处理批次根因；无阻断根因时才进入策略迭代
```

普通 GEO 调研继续使用七步任务图；发布后复测只执行 `frontend_baseline`。两者不再共用会生成新蓝图的完整任务图。

## 二、已整改的高风险冲突

### 1. 复测任务图与递归风险

- 原问题：`post_publish_retest` 复用七步任务图，会再次生成待批准蓝图，且可能被编排器继续识别为下一轮复测来源。
- 整改：增加按触发类型选择的确定性任务图；复测图只有 `frontend_baseline`，任务完成即将 run 置为 `completed`。
- 用户影响：复测从“再跑一遍调研”变为真正的测量任务，减少模型调用、等待时间和错误状态。

### 2. KPI 事实源错误

- 原问题：真实 `answerPack.observations` 已采集，但 `mention_baseline` 仍由模型的结构化语义输出推导，文档所称“真实观测 KPI”与代码不一致。
- 整改：新增 `buildGeoMentionBaselineFromObservations`，按问题和 Provider 的成功观测确定性计算提及率、成功/失败样本数、Provider 分布和渠道引用分布；新 run 标记 `measurementSource=model_answer_observations`。某问题全部 Provider 失败时标为 `unevaluableQuestions` 并从分母剔除；整轮无成功样本则拒绝写 KPI。
- 兼容：历史记录保留 `legacy_semantic_output` 标记，避免伪装成同口径数据。
- 用户影响：KPI 可以追溯到真实回答样本；Provider 失败不再被误当成“未提及”。

### 3. 发布闭环与 GEO 复测顺序冲突

- 原问题：复测只看蓝图批准时间，没有证明相关内容已发布并完成存活/AI 样本闭环；与已有发布批次优化快照形成两条并行闭环。
- 整改：复测必须绑定 `blueprintVersionId`、原始 `baselineRunId`、当前蓝图对应的 `strategyPackId`、已闭合 `batchKey`、`optimizationSnapshotId` 和 `inputEvidenceHash`；批次必须由当前蓝图策略包产生、在蓝图批准后生成且 `batchClosed=true`。
- 编排：复测间隔从蓝图批准与批次闭合的较晚时间起算；同蓝图、同批次幂等；低 KPI 时先执行批次快照里的 `fix_site`、`collect_evidence`、`continue_monitoring`、`manual_review` 等根因动作。
- 用户影响：不会在内容尚未真实发布或证据尚未闭合时给出“推广无效”的误判，也不会用更多内容掩盖官网或发布故障。
- 口径提示：前后 delta 是观测变化，不是单凭时间先后就成立的因果证明；运行详情页已去除“内容带来增量”的因果化措辞。

### 4. 平台查询被预算截断

- 原问题：平台 `site:` 查询与核心查询一起被 `maxQueries` 截断，配置了多个目标平台也可能一条都不执行；零命中渠道不会进入 `channelStats`，补充轮无法识别平台缺口。
- 整改：核心查询最多 6 条，研究边界内每个第三方目标渠道使用独立平台查询预算；规则包先按 `targetChannels` 过滤；统计预置零值目标渠道；零命中时定向补平台证据。
- 用户影响：声明的平台才会被搜索，每个目标平台都有最少一次检索机会；代价是请求量随目标平台数线性增加。

### 5. 规则包只在读取路径守门

- 原问题：就绪检查会阻塞缺失规则包，但直接调用启动 API 仍可能绕过；`activatedBy/activatedAt` 只是可选字段，无法证明规则包已激活。
- 整改：激活人和激活时间变为解析必填；覆盖校验同时落在 workspace 就绪检查、service 启动和 repository 写事务前。
- 用户影响：页面、API、内部调用使用同一准入标准；错误会附带缺包、缺渠道或激活元数据非法的具体原因。

### 6. 平台策略证据跨渠道挂靠

- 原问题：`platformStrategy.evidenceBasis` 只检查候选是否存在，没有验证候选和 URL 是否属于声明渠道。
- 整改：候选 ID 必须存在且 `candidate.channelKey` 与策略渠道一致；URL 也必须映射到同渠道候选；修剪后无依据则确定性降级为 `hypothesis=true`。
- 用户影响：一个平台的证据不能再替另一个平台背书。

## 三、契约与兼容性

- 数据库沿用现有 `mention_baseline` JSON 列，本次不新增迁移。
- `GeoMentionBaseline` 新字段均为可选，旧记录可继续读取。
- 普通调研仍保持七步图、人工批准和既有幂等结构。
- `post_publish_retest` 的语义有意收紧：手工或自动创建都要求批准蓝图和已闭合发布批次。
- 第三方渠道规则包的环境变量模式仍保留，但现在必须携带有效 `activatedBy`、`activatedAt`；仅自有渠道不要求规则包。

## 五、保留风险

- 当前规则包仍由环境变量承载；`activatedBy/activatedAt` 可校验格式，但不能替代治理表中的人工激活动作和不可变审计日志。
- 本次只验证本地契约与回归测试，没有替用户执行数据库迁移、真实 Provider 计费调用或生产发布。
- 目标第三方渠道越多，搜索成本越高；应把研究边界限制为本轮真正要运营的平台。
