# 公众号 cc2image 智能配图链路接入规划

## 结论

最顺的接入方式不是把 `cc2image` 当成一个外部页面或运行中的服务，而是把它的“文章拆图方法、风格库、Prompt 规范、三候选人工确认门禁”改造成工作台内部的视觉方案层，插在“正文完成”与“公众号排版预览”之间。

目标链路为：

```text
正文定稿
→ 系统提取认知锚点并推荐 3 条视觉路线
→ 并行生成 3 张封面候选
→ 人工选定封面与系列视觉方向
→ 每个正文认知锚点生成 3 张同风格构图候选
→ 人工批量选择或跳过
→ 自动写入现有素材图库与正文绑定
→ 重新生成公众号 HTML 预览
→ 人工确认
→ 写入公众号草稿箱
```

首期在当前 `/free-production` 单篇文章页落地，因为这里已经具备完整的封面、正文配图、素材图库、公众号 CDN 转存和草稿创建能力。视觉引擎必须做成与业务入口解耦的共享模块，第二阶段再接入 `MonthlyPlan -> date execution -> publish and metrics` 中的月度文章生产节点，不另建独立计划周期。

## 本次实施状态（2026-08-20）

已完成推荐的首个开发切片：

- 当前公众号正文自动提取最多 3 个正文认知锚点，并从 12 套 production allowlist 中确定三条不同封面路线。
- 在原文章预览页内生成并比较“品牌稳妥型、系统解释型、传播张力型”3 个封面候选。
- 用户人工选择后，候选图进入原 `wechat_cover -> workbench-cover:<batchId> -> WechatSync` 发布链路；手动上传继续作为兜底。
- 视觉计划绑定 `artifactId + sourceContentHash`；正文变化后旧计划显示为 `stale`。
- Provider 未配置、单张生成失败和部分成功都有可见状态，不影响正文与已有封面。
- Prompt、候选存储引用和密钥不进入浏览器响应；候选文件带 SHA-256 完整性校验。
- 已发布批次保留视觉历史只读能力，禁止重新生成或更换封面。

本切片有意未扩展到正文图生成：正文锚点已经进入同一 `WechatVisualPlan`，下一切片复用这些锚点实现“每个位置 3 张同系列候选、选择后写入素材图库和正文绑定”。当前图片生成仍在请求内并行等待；接入生产 Provider 并完成真实时延验证后，再决定是否升级为 durable worker，避免在尚未验证调用规模前先引入额外队列复杂度。

## 一、前置判断

### 1. 核心问题

当前工作台能上传封面、从素材图库为正文配图建议绑定图片，但不能基于当前文章自动完成视觉理解、候选生成和三选一。现有 `scripts/wechat-image-prompt-library.mjs` 已有 12 套精选风格、推荐规则、Prompt 渲染和事实门禁，但只接受人工确认后的 shot list，不负责文章拆解、图片生成、候选选择和回填。

### 2. 最终目标

用户不离开当前文章页，不复制正文、不手工转存图片，能够：

- 一次操作获得 3 张有明确推荐理由的封面。
- 选中封面后，系统以同一系列视觉方向为每个正文认知锚点提供 3 张配图候选。
- 一键应用全部选择，立即在公众号正文预览中看到结果。
- 保留手动上传、图库选择、单组重生和跳过正文图的能力。

### 3. 成本最低的路径

复用现有链路，不重做以下能力：

- `MediaLibraryAsset` 图片存储和内容接口。
- `workbench-media:<assetId>` 正文稳定引用。
- `workbench-media://<assetId>` 发布前微信 CDN 转存。
- `wechat_cover` 必需素材门禁和 `workbench-cover:<batchId>` 发布契约。
- `VisualAssetBindingPanel` 正文绑定与 `WechatCoverBindingPanel` 封面预览。
- 正文变化后重新渲染 `wechatPresentation`、刷新 `htmlHash` 和撤销已确认摘要的机制。

新增能力只覆盖“视觉理解、候选生成、选择记录、生成资产入库”。

### 4. 不采用的路径

- 不在生产运行时拉取 GitHub 仓库或执行上游 Python 脚本。
- 不把 Codex Desktop 的 `image_gen` 工具当作工作台后端 API；它不是部署后的稳定运行契约。
- 不新增一个独立“配图中心”要求用户来回切页。
- 不让每张正文图使用完全不同的画风。
- 不一次生成 3 套完整文章视觉包；中等文章会迅速膨胀到十几至几十张图片，等待和成本都不可控。

### 5. 主要负面影响

- 每个正文位置 3 个候选会把图片调用量放大 3 倍。
- 文章修改后，视觉建议和已选结果可能失效。
- 生图模型的中文文字、数据准确性和品牌一致性不可直接信任。
- 上游 `cc2image` 会持续变化，直接跟随 `main` 会导致风格和 Prompt 漂移。

对应措施分别是两阶段生成、内容哈希失效、后期文字排版与人工确认、上游版本锁定。

## 二、对 cc2image 的正确定位

`cc2image` 是面向 Codex 的 Skill 仓库，不是 npm 包、HTTP 服务或图片 Provider。它的核心资产包括：

- 文章主题、目标读者、核心观点和认知锚点提取方法。
- 49 套内容风格与风格匹配规则。
- 封面、正文图的 Prompt 模板和质量约束。
- “推荐 3 种方向并由人确认”的交互门禁。
- `prompt_schema.py` 等确定性 Prompt 组装脚本。

工作台接入时应做“产品化改编”，而不是逐条执行 Skill：

| cc2image 原能力 | 工作台对应实现 |
| --- | --- |
| `Visualize:visualize` 选择器 | 当前文章页内的三候选视觉工作台 |
| 对话中确认 `style_id` | 用户选中一张封面，自动确认系列视觉方向 |
| `image_gen` | 工作台自有 `ImageGenerationProvider` 适配层 |
| JSON / Markdown 拆图清单 | 版本化 `WechatVisualPlan` 数据契约 |
| 生成后人工查看 | 候选审核、批量应用和公众号 HTML 预览 |
| 临时任务图片 | 进入现有产品素材图库并保留生成溯源 |

上游首个锁定基线：

- Repository：<https://github.com/izscc/cc2image>
- Commit：`33b18b399fcfc6a54a7c4cc2d137fa3dfd3afad8`
- License：MIT，保留 `Copyright (c) 2026 izscc`、MIT License 和来源说明。

生产环境不依赖 GitHub 可用性。上游内容以版本化快照进入仓库，升级通过人工执行的 diff 和回归测试完成。

## 三、推荐交互

### 阶段 A：三张封面确定视觉路线

正文生成并完成来源核对后，现有封面区域显示主操作“生成 3 个封面方案”。系统先做文章视觉分析，再生成三个刻意有差异的方向：

1. 品牌稳妥型：优先 JOTO 官方、产品可信感和清晰标题安全区。
2. 系统解释型：优先流程、结构、工作流和认知图解。
3. 传播张力型：优先视觉隐喻、情绪钩子和社交传播记忆点。

三张卡片展示封面、中文风格名和一行推荐理由。第一项标记“最推荐”，但不能自动选中。用户可选择一张，或只重生某一张。

封面规格以现有公众号发布封面为准，目标比例统一为 `2.35:1`。如果图片 Provider 不能直接输出该比例，先生成最接近的宽图，再在服务端进行安全裁切和标题区合成。

### 阶段 B：正文认知锚点三选一

用户选中封面后，系统确认整篇文章的系列视觉方向，再生成正文图。这样正文图不会出现三种毫无关系的画风。

首期默认从文章中选择最多 3 个高价值认知锚点，每个锚点生成 3 个候选：

- 候选 1：最清晰的结构表达。
- 候选 2：不同构图或视觉隐喻。
- 候选 3：不同信息密度或叙事视角。

三个候选保持同一 `styleId`、主色、线条/材质和角色设定，只改变构图、隐喻、动作或解释度。正文图默认 `16:9`，一个候选只表达一个核心判断。

认知锚点优先级：

1. 文章核心判断。
2. 旧流程与新流程的关键断点或对比。
3. 输入、处理、输出和反馈闭环。
4. 实施路径、分流条件或常见坑。
5. 角色状态变化或产品价值承接点。

### 阶段 C：一次应用

用户完成选择后点击“应用已选封面和配图”。系统在一个受控操作中：

1. 把选中候选写入素材图库。
2. 将封面候选绑定为当前批次 `wechat_cover`。
3. 将正文候选绑定到对应 `VisualMaterialSuggestion`。
4. 重新生成 `previewHtml` 和 `publishHtml`。
5. 更新 `htmlHash`、`contentDigest` 和版本号。
6. 撤销旧的正文确认状态，要求用户查看最新公众号预览。

未选中的候选保留短期缓存，不进入正式素材图库；达到保留期限后可由清理任务删除。单个正文锚点允许跳过，封面仍维持公众号发布必需门禁。

## 四、系统结构

```text
ContentDraftArtifact / DraftVersion
        │ sourceContentHash
        ▼
WechatVisualPlanningService
  ├─ 文章理解与认知锚点提取（文本模型）
  ├─ cc2image 风格推荐与 Prompt 编译（确定性规则）
  └─ 事实、品牌与文字策略门禁
        │ WechatVisualPlan
        ▼
VisualGenerationQueue
        │
        ▼
ImageGenerationProvider
  ├─ provider adapter
  ├─ 超时、限流、重试与幂等
  └─ 图片格式归一化与安全检查
        │
        ▼
VisualCandidateStore
        │ 人工三选一
        ▼
MediaLibrary + Cover Binding
        │
        ▼
JOTO WeChat Renderer
        │
        ▼
WechatSync → 微信 CDN / 草稿箱
```

### 1. 视觉规划层

文本模型只负责把当前正式正文转换成结构化视觉计划，不直接决定发布：

```ts
interface WechatVisualPlan {
  planId: string;
  ownerType: "free_production" | "monthly_article";
  ownerId: string;
  draftArtifactId: string;
  sourceContentHash: string;
  articleTitle: string;
  targetAudience: string;
  coreJudgment: string;
  recommendedBodyCount: number;
  styleRoutes: VisualStyleRoute[];
  anchors: VisualAnchor[];
  promptLibraryVersion: string;
  cc2imageCommit: string;
  status: "planning" | "cover_generating" | "cover_selection" | "body_generating" | "body_selection" | "applied" | "stale" | "failed";
  version: number;
}
```

`VisualAnchor` 至少保存 `sectionKey`、原文定位、`coreIdea`、`visualAnchor`、`visualType`、`structure`、`mainAction`、`shortLabels`、证据引用和风险标记。生成 Prompt 前必须经过 schema 校验；涉及数字、排名、效果或产品能力时，必须关联已核验来源，否则删除量化表达或阻断生成。

### 2. 风格与 Prompt 层

首期不直接开放全部 49 套风格。工作台已有 12 套经过 JOTO 场景改写的风格，应先作为 production allowlist；上游 49 套保留在版本快照中，完成品牌、中文、公众号比例和安全回归后再逐批启用。

需要把现有 `scripts/wechat-image-prompt-library.mjs` 拆成可被服务端直接调用的 TypeScript 模块：

- `wechat-visual-style-registry.ts`：风格定义和适用场景。
- `wechat-visual-recommender.ts`：三条视觉路线推荐。
- `wechat-visual-prompt-compiler.ts`：封面和正文 Prompt 编译。
- `wechat-visual-validator.ts`：证据、文字、品牌和隐私门禁。

图片模型不负责生成最终中文标题。默认 `textPolicy` 使用 `post_layout`：生图阶段为标题和短标签预留安全区，最终中文标题、JOTO 品牌元素和必要短标签由确定性后处理合成。正文图尽量用结构、动作和物件表达，详细文字继续由 HTML 图注承载。

### 3. 图片 Provider 层

当前 `src/lib/ai-provider.ts` 只支持文本 `/chat/completions`，不能承担图片生成。新增独立接口：

```ts
interface ImageGenerationProvider {
  generate(input: {
    prompt: string;
    aspectRatio: "2.35:1" | "16:9";
    referenceAssetIds?: string[];
    idempotencyKey: string;
  }): Promise<{
    provider: string;
    model: string;
    requestId?: string;
    mimeType: "image/png" | "image/jpeg" | "image/webp";
    bytes: Uint8Array;
    width: number;
    height: number;
  }>;
}
```

首期只实现一个真实 Provider，接口保持可替换。Provider 密钥只从服务端环境变量读取，不进入计划、日志、审计、浏览器响应或 Prompt 快照。生成失败按候选组重试，不能导致正文、已选封面或已成功候选丢失。

### 4. 任务与并发

图片生成必须走独立 durable worker，不在 Next.js 请求内等待整批完成：

- API 创建视觉计划和生成任务后立即返回。
- 页面轮询或使用现有任务状态机制展示逐张完成进度。
- 封面候选优先级高于正文候选。
- 单篇文章默认并发 2，防止 Provider 限流和本机内存峰值。
- 单个候选最多自动重试 1 次；继续失败时给出“只重试这一张”。
- 幂等键包含 `planId + candidateGroupId + variantIndex + promptHash`。

### 5. 存储与发布复用

扩展 `MediaLibraryAssetRecord`，增加可选生成溯源：

```ts
generation?: {
  source: "ai_generated";
  visualPlanId: string;
  candidateId: string;
  role: "cover" | "body";
  styleId: string;
  promptHash: string;
  provider: string;
  model: string;
  width: number;
  height: number;
};
```

未选候选先存入独立 candidate storage。用户应用后才转为正式 `MediaLibraryAsset`，避免素材图库被大量废稿污染。

封面不改变对 WechatSync 的发布 payload。现有封面内容接口扩展为同时解析本地上传 `free-asset-*` 和已选生成素材引用；发布仍传 `workbench-cover:<batchId>`。正文图继续使用 `workbench-media://<assetId>`，发布前由现有 bridge 转存微信 CDN。

## 五、接口建议

```text
POST  /api/v5/free-production/batches/:id/visual-plans
GET   /api/v5/free-production/batches/:id/visual-plans/current
POST  /api/v5/free-production/batches/:id/visual-plans/:planId/cover-generation
PATCH /api/v5/free-production/batches/:id/visual-plans/:planId/cover-selection
POST  /api/v5/free-production/batches/:id/visual-plans/:planId/body-generation
PATCH /api/v5/free-production/batches/:id/visual-plans/:planId/selections
POST  /api/v5/free-production/batches/:id/visual-plans/:planId/apply
POST  /api/v5/free-production/batches/:id/visual-plans/:planId/candidates/:candidateId/retry
```

所有写接口延续现有 `expectedVersion`、`x-idempotency-key`、`auditReason` 和操作者审计规则。`apply` 必须原子校验当前正文版本、计划版本、候选完整性、产品归属和图片安全状态。

第二阶段为月度文章提供同一 service 的路由适配，不复制视觉规划、Provider、候选存储或 Prompt 编译逻辑。

## 六、页面落点

现有 `WechatArticlePreview` 内的封面绑定和配图工位升级为一个内嵌 `WechatVisualStudio`：

1. 顶部：生成状态、已选视觉路线、全部重生入口。
2. 封面区：3 张大图卡片，展示推荐理由和单张重生。
3. 正文区：按认知锚点折叠，每组 3 张候选，可选、跳过或单组重生。
4. 底部固定操作：`应用已选封面和配图`。
5. 高级信息折叠区：风格名、模型、版本、生成时间；完整 Prompt 默认不展示。

页面不新增逐项参数表单。系统自动推断文章长度、图片数量、认知锚点、比例和三条推荐方向，只让用户承担最终视觉判断。

## 七、内容变更与失效规则

- 视觉计划绑定 `draftArtifactId + sourceContentHash`。
- 标题、摘要或正文变化后，未应用候选立即标记 `stale`。
- 已应用图片不直接删除，但发布门禁提示“正文已变化，确认沿用或重新生成视觉方案”。
- 用户明确确认沿用时记录审计；涉及标题变化的封面必须重新合成准确中文标题。
- 更换排版模板只重新渲染 HTML，不要求重新生图。
- 更换产品、文章类型或目标受众时必须重新生成视觉计划。

## 八、分阶段实施

### P0：视觉内核与契约

- 锁定并保存 cc2image 上游版本、MIT License 和 NOTICE。
- 将现有 12 套风格迁移为 TypeScript production allowlist。
- 建立 `WechatVisualPlan`、candidate、selection 和 generation run 契约。
- 建立文章拆图 JSON schema、Prompt 编译和证据门禁测试。
- 增加一个图片 Provider adapter 和配置状态检查。

### P1：当前单篇公众号文章闭环

- `/free-production` 内生成 3 张封面候选。
- 选定视觉路线后，为最多 3 个认知锚点各生成 3 张候选。
- 完成批量选择、单张重生、跳过和原子应用。
- 复用素材图库、封面接口、公众号 HTML 和 WechatSync 发布。
- 保留原手动上传和图库选择作为降级路径。

### P2：月度文章生产复用

- 在月度正式文章的 `DraftVersion` 节点接入同一视觉引擎。
- 视觉选择进入现有人工审核与公众号呈现工件。
- 将视觉版本、Provider 结果和最终选择写入月度文章审计链，不产生独立规划周期。

### P3：效果复盘与自动优化

- 记录视觉方案采用率、单组重生率、人工上传替代率和完成耗时。
- 把已发布文章的封面/正文图选择与阅读、分享等指标建立关联。
- 只有在积累足够真实样本后，调整三条视觉路线的排序和 production allowlist。

## 九、MVP 验收标准

### 核心验收

- 当前公众号正文完成后，用户能在原页生成 3 张封面候选，且每张有可理解的推荐理由。
- 用户选定封面后，系统能为最多 3 个正文认知锚点各生成 3 张同系列候选。
- 用户可只重生一张、跳过单个正文锚点，并一次应用全部选择。
- 应用后公众号预览立即显示选中的正文图，封面区域显示选中封面。
- 正式发布继续使用现有封面和微信 CDN 转存链路，不出现内部本地路径。
- 文章变化后旧视觉计划可被明确识别为失效，不会静默发布旧图。
- 任一 Provider 失败不丢失正文、其他已成功候选或人工上传素材。

### 质量门禁

- 未经人工选中的候选不得进入正式发布 HTML。
- 数字、排名、客户、效果和产品能力不得由图片新增未经证据支持的主张。
- 最终中文标题必须准确，图片模型生成的错误中文不能直接发布。
- 图片不得包含水印、内部路径、生产标识、密钥、手机号或隐私信息。
- 生成素材必须归属当前产品并通过 MIME、文件摘要、尺寸和大小检查。

## 十、成功指标

首期不以“生成图片数量”为成功，而以减少外部搬运和提升可发布率为准：

- 视觉方案采用率：生成过方案的文章中，至少选择并应用一个生成候选的比例。
- 外部搬运降低：人工下载、改名、上传和重新绑定的次数。
- 首次可用率：无需重生即可被选中的候选组比例。
- 完成耗时：从点击生成视觉方案到应用完成的时间。
- 发布守门：生成图片导致的发布阻断、错误中文和事实误导必须保持为零。

## 十一、风险与整改

| 风险 | 用户影响 | 整改方案 |
| --- | --- | --- |
| 每个锚点生成 3 张导致成本和等待上升 | 页面长时间等待，单篇成本不可控 | 封面先行、正文后生成；首期最多 3 个锚点；逐张返回；只重试失败组 |
| 三种推荐造成整篇风格混乱 | 文章像素材拼盘 | 三封面用于确定系列路线；正文三候选只改构图，不改系列风格 |
| 中文文字错误 | 封面不可直接发布 | 默认 `post_layout`，模型不生成正式标题，服务端确定性合成中文 |
| 图片暗示未经证实的数据或能力 | 品牌与合规风险 | 视觉锚点绑定来源；数字主张门禁；人工选择；发布前审计 |
| 上游 Skill 更新导致结果漂移 | 同类文章前后视觉不一致 | 锁定 commit 和 Prompt 版本；人工升级；回归后才启用 |
| 候选图污染素材图库 | 图库难以检索和维护 | 未选候选独立短期存储，应用后才进入正式图库 |
| Provider 故障 | 用户无法完成配图 | 状态可见、组级重试、保留已有结果、手动上传和图库选择始终可用 |
| 正文修改后沿用旧图 | 图文不一致 | `sourceContentHash` 失效；沿用需再次明确确认并审计 |

## 十二、明确不在首期范围

- 一次生成 3 套完整文章视觉包。
- 默认开放全部 49 套风格和 8 套图标模式。
- 自动跳过人工选择直接发布生成图片。
- 自动根据阅读数据更换已发布文章封面。
- 把未选候选长期保存在正式素材图库。
- 为配图建立独立于文章和月度业务流的计划、审核或复盘周期。

## 十三、推荐的首个开发切片

先完成最小纵向闭环：

```text
当前正文
→ 结构化视觉计划
→ 3 张封面候选
→ 选择 1 张
→ 进入现有封面发布链路
```

这个切片先验证图片 Provider、候选存储、版本失效、中文标题合成和公众号封面发布是否可靠。验证通过后，再复用同一套 candidate group 和选择机制扩展到正文锚点，避免封面与正文同时开工导致排错范围过大。
