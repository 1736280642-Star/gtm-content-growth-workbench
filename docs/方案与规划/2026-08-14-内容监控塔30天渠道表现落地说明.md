# 内容监控塔 30 天渠道表现落地说明

## 结论

本次在现有 `GEO 监控塔` 总览中落地近 30 天内容表现模块，页面名称暂不变。模块只统计已进入正式发布链路的微信公众号、CSDN、掘金、知乎内容，展示发布数、浏览量、点赞数、收藏数、趋势和渠道拆分。

## 实现逻辑

1. 发布数以 `content_publish_result` 为主；历史恢复数据尚未生成发布结果行时，回退到正式 `MonthlyWorkspace` 的已发布任务。
2. 平台指标写入 append-only 的 `content_metric_snapshot`，保留每次采集时间、指标日期、来源和原始数据哈希，不覆盖历史快照。
3. 总览 API 将累计快照换算为每日新增，再按近 30 天聚合；趋势图一次只展示一个指标，避免发布数与浏览量量级不同导致图表失真。
4. 同步 API 只允许调用本机采集器，按平台分别记录同步状态。采集器未配置时返回 `pending_config`，页面继续展示真实发布数并明确标注指标待回传，不生成模拟数据。

## 底层原因与用户影响

- 四个平台后台能力和授权方式不同，网页端不直接持有平台凭证，降低凭证泄漏和前台任务超时风险。
- 用矩阵任务 ID 作为稳定业务身份，兼容历史恢复内容；后续补齐正式发布结果行时无需迁移已有指标。
- 快照不可变，后续可以追溯异常增长、重算趋势，并为月度复盘提供可信依据。
- 当前没有平台后台回传时，浏览、点赞、收藏会显示为 `0 / 待回传`，不会让用户误以为这是平台确认的零数据。

## 运行配置

- `CONTENT_METRICS_RUNNER_URL`：本机采集器地址，例如 `http://127.0.0.1:<port>`。
- `CONTENT_METRICS_RUNNER_TOKEN`：工作台与本机采集器之间的鉴权令牌。
- 数据库升级：运行 `npm.cmd run init:mysql` 应用 `20260814_030_v5_content_metric_snapshots.sql`。

### 本地运行

1. 在 `.env.local` 配置采集器 URL、Token 以及四个平台凭证。
2. 运行 `npm.cmd run metrics:runner` 启动本机采集器。
3. 运行 `npm.cmd run worker:content-metrics` 启动自动同步 Worker；默认间隔为 `21600` 秒。

### 3027 Docker 运行

执行 `npm.cmd run docker:3027` 后会创建两个独立服务：

- `content-metrics-runner`：提供 `/health`、`/auth/status`、`/metrics/pull`，不映射宿主机端口。
- `content-metrics-worker`：只在 Compose 私有网络中访问工作台与采集器，每 6 小时发起一次同步。

两个服务与 GEO 调研 Worker 没有依赖关系，不共用任务队列、轮询周期或健康状态。

### 平台适配器

- 微信公众号：使用官方 access token 与图文数据接口。
- CSDN：默认解析已发布文章页；后台接口变化时通过 `CSDN_METRICS_URL_TEMPLATE` 与 `CSDN_METRICS_PATHS_JSON` 覆盖。
- 掘金：默认读取文章详情接口，也支持同名 `METRICS_URL_TEMPLATE` 与 `METRICS_PATHS_JSON` 覆盖。
- 知乎：默认读取文章详情接口，也支持覆盖 URL 与字段路径。

Cookie 平台建议配置 `*_METRICS_AUTH_CHECK_URL`。缺少检查地址时配置中心会显示“已配置但待验证”，不会把“存在 Cookie”误判为“授权有效”。

平台账号、Cookie、Token 只保存在本机采集器的安全存储中，不写入仓库、浏览器或业务数据库。

## 验收与复盘

- 验收发布数与正式月度工作区一致。
- 验收单指标趋势、每日新增/累计切换和渠道筛选。
- 验收采集器缺失、授权失效、平台失败时的显式状态。
- 每月复盘指标覆盖率；覆盖率不足时先修复采集链路，不用缺失值代替真实后台数据。

后续将导航与页面标题从 `GEO 监控塔` 统一改为 `内容监控塔`，本次不提前改名。
