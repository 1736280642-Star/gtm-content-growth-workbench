# GEO 真实用户问题目录闭环

## 结论

现有 GEO 研究 Agent 已具备联网搜索、公开来源留存和问题机会发现能力。本次补齐“按产品打包问题目录、人工复核、批量收录正式问题池”的最后一段链路。

## 实现逻辑

```text
产品与研究边界
→ 联网研究规划
→ 多来源真实用户问题发现
→ 逐条公开 URL 校验
→ 按用户旅程模块形成产品问题目录
→ 人工选择并确认
→ 问题池自动去重、留存来源与算法轨迹
→ 待产品知识证据补齐后进入月度内容策略
```

问题发现覆盖搜索意图、问答社区、论坛、评论、社交讨论、Issue 讨论和官方支持社区，并使用产品名称、别名及品类词扩展查询。模型输出必须包含自然语言问题、意图、受众、模块、来源类型、公开 URL、优先级、建议文章类型和关键词。

## 底层原因

- “有人在问”与“产品答案成立”是两类证据。公开讨论来源只证明需求存在，不能直接成为产品能力事实。
- 问题目录属于选题资产，正式问题池属于治理资产。两者之间必须保留人工确认，避免 Agent 自动改变月度内容方向。
- 研究发现与问题池使用不同存储适配器，因此写入采用双侧幂等键；中途失败后可以安全重试，不重复创建问题。

## 用户影响

- 每个产品的研究运行都会展示独立的“用户问题目录”。
- 只有逐条绑定可复核公开来源的问题才能选择。
- 可一次选择多条或全选未收录问题，确认后批量进入问题池。
- 新收录问题默认标记为观察状态和证据缺口，不会自动加入月度计划或触发文章生成。
- 重复或近似问题继续由现有问题标准化与冲突识别逻辑处理。

## 风险与后续

- 当前搜索质量依赖 OpenAI Responses API 的 `web_search` 可用性、查询覆盖度和公开网页可访问性。
- 搜索结果 URL 证明问题需求，但不保证来源文本长期可访问；后续可增加页面快照与摘录级定位。
- 模块和文章类型目前由研究结果提供，并有规则兜底；高价值目录积累三次以上后，应沉淀跨产品通用模块词表和来源质量评分规则。
