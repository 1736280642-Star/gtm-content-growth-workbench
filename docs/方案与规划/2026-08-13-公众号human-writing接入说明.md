# 公众号 human-writing 接入说明

## 结论

工作台不直接读取开发机上的 `SKILL.md`。本机 Skill 路径无法随应用部署，也不能成为正式生产的规则来源。当前实现把 `human-writing` 中适用于微信公众号非虚构写作的稳定规则整理成版本化配置，并同时接入自由单篇生产和正式生产合同。

## 实现逻辑

共享规则位于 `src/lib/v5/human-writing-wechat.ts`，版本为 `human-writing.wechat.v1.1.0`。该模块提供三项能力。

1. 识别公众号渠道，包括 `wechat`、`wechat_official_account` 和中文渠道名。
2. 向模型提供材料边界、段落推进、自然中文和成稿禁令。
3. 确定性检查破折号、翻案腔、提示性冒号、模型路标和总结式结尾。

自由单篇生产在 `free-production-service.ts` 中把规则版本和写作指令加入模型输入，随后由 `free-production-output-validator.ts` 检查成稿。

正式生产在 `production-contract-compiler.ts` 中把规则编入冻结合同。单篇、样稿和月度批量生产都会继承同一组指令。`production-output-validator.ts` 与 `formal-generation-service.ts` 负责最终拦截，模型自检只作为辅助。

## 底层原因

Prompt 只能提高模型遵循规则的概率，无法保证每次都合格。工作台原有架构要求正式合同负责固定规则，确定性校验器负责判断成稿能否使用。因此，本次接入保留了这条依赖方向，没有把 Skill 路径、产品事实或写作判断写进前端。

文章事实仍然只能来自 EvidencePack、知识快照和人工补充材料。`human-writing` 决定怎样写，不能替代事实来源，也不能绕过证据门禁。

## 对使用者的影响

公众号内容会更少出现机构腔、翻案句和模型式总结。材料不足时，模型被要求缩短内容或收窄问题，不能依靠假案例和重复解释填满篇幅。

成稿命中硬规则时，系统将它列为可修复问题，并沿用现有的一次自动修复上限。修复后仍不合格，正文不会进入可发布状态。其他渠道不会继承公众号专属限制。

## 维护方式

升级写作规则时先修改共享模块版本，再更新两条生产链路的测试。不要在页面、单个文章类型或某个 Provider 的 Prompt 中复制一份规则。需要新增难以用字符串判断的写作要求时，先作为 Prompt 指令观察样稿，再决定是否加入确定性门禁，避免误伤正常中文。
