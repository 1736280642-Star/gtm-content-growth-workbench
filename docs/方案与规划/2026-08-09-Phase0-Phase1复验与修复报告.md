# Phase 0–Phase 1 复验与修复报告

> 复验日期：2026-08-09  
> 验收基线：《2026-08-06-GEO全自动闭环开发前文档》  
> 辅助依据：8 月 5–9 日方案、MCP 契约、Phase 0/1 开发报告及 8 月 9 日工作区实际修改

> **后续整改更新**：本报告记录的是首次复验结论。其后已补充产品策略确定性编译、账号容量排程、一次性设备配对、证据到策略执行调整、下一月正式 MonthlyPlan 溢出写入，并重构内容自动化、GEO 监控塔、设置和月度复盘。最新实现与仍未通过的真实外部验收边界见《2026-08-09-页面与功能优化整改报告》。

## 一、结论

Phase 0 未通过整体验收，Phase 1 部分通过。

原验收主要依赖 TypeScript 与“文件/关键字存在”检查，无法证明功能可启动、会持久化或能跑通业务。因此出现了结构检查 305/305 通过，但 5 个新增 MCP Server 无法被 Node.js 解析、多个写接口返回成功却不写数据库的情况。

本次已修复可在当前范围内确定的问题，并把不能安全伪装成完成的月末迁移改为失败关闭。剩余未通过项不会顺延成“默认完成”。

## 三、已修复问题

### 3.1 MCP 可执行性与验收漏洞

- 移除 5 个 `.mjs` 中 Node.js 无法解析的 TypeScript 标注。
- 新增 `test:mcp-phase1`：真实完成 MCP 初始化、工具发现和工具调用。
- `validate:structure` 增加 `node --check`，以后不能再以“文件存在”冒充“Server 可用”。
- 修正 Capture MCP 的必填参数与任务查询路径。

### 3.2 写接口伪成功

- Capture 设备、任务、租约、证据和归因链改为 MySQL 持久化。
- 产品推广开关改为更新正式 `product_entity`，并写治理审计。
- 产品列表读取正式推广状态，页面刷新后不会恢复旧值。
- 资料快照重建改为调用真实知识刷新与 RAG 索引快照流程。
- 策略包查看与应用改为读取/更新 `product_strategy_packs`，缺少蓝图、资料快照或内容计划时失败关闭。
- 设置页修复 API envelope 读取错误；原实现即使后端返回设备也始终显示空列表。

### 3.3 数据模型与迁移

- 原迁移错误修改不存在的 `products`、`production_tasks`、`publish_schedules`；现对齐正式真相源 `product_entity` 与 `content_matrix_item`。
- 补齐 `next_automatic_action`，证据增加 `(task_id, artifact_hash)` 唯一约束。
- 修复 `init:mysql` 与现有迁移台账 `name/checksum` 的兼容问题。
- 为不支持 `ADD COLUMN IF NOT EXISTS` 的 MySQL 版本增加可移植执行逻辑。
- 已在当前 MySQL 成功应用 `20260809_017_v5_phase1_mcp_capture.sql`。

### 3.4 责任模型

- 发布监控不再维护第二套危险状态集合。
- 普通失败在三次重试耗尽前保持 `system/retrying`；认证失效、平台拒绝、风控、人工接管等仍直接进入用户责任。
- 当日执行页、发布监控页、首页和责任 API 使用同一分类函数。

## 五、剩余整改顺序

1. 实现跨月正式快照迁移：创建/锁定下一月 MonthlyPlan 与 ContentMatrix 版本，复制未完成任务，保留来源关联和幂等键，事务提交后才能开放 POST。
2. 统一“产品策略包”领域真相：明确 `product_strategy_packs` 与正式 `rule_package_version`、`monthly_strategy_package_version` 的关系，避免三套策略包并存。
3. 完成 Capture 安全闭环：一次性配对码、短期设备凭证、刷新/撤销、workspace/user/device 授权校验；当前不能对外宣称“设备配对完成”。
4. 选择一个真实产品执行只读预检与受控 E2E；外部正式发布需明确使用测试账号/内容和回滚方案，记录运行 ID、公开 URL、回传、重试与审计证据。

## 六、对使用者的影响

修复后，用户操作不会再因为接口返回临时对象而看到虚假的“已配对、已推广、已迁移”。可恢复故障不会过早进入“需你处理”；真正缺少持久化能力的月末迁移会明确报错并给出下一步，而不是在下个月发现任务实际丢失。
