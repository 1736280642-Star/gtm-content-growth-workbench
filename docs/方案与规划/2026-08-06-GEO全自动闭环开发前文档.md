## 一、文档目的与范围

### 1.1 背景与目标

用户只需上传产品资料并完成一次性授权，系统自动完成 GEO 调研、内容铺设、品牌与 AI 回答监控、策略迭代的完整闭环。本阶段目标是让主链路确定、可重试、可恢复、可观测，并接入 AgentTeams 作为协同编排层。

### 1.2 本次开发范围（In Scope）

- 确定性执行引擎补全：产品策略包编译、后台正文生成、账号容量排程、发布回传、统一责任判定器。
- MCP 契约化：把现有能力暴露为 5-6 个 MCP Server。
- capture-devices：采集设备配对、任务矩阵、Lease、心跳、工件上传。
- AgentTeams 编排层接入（Docker 本地模式）：Manager + 职能 Workers + Human 映射 + Matrix 通知。
- 页面改造（详见页面功能改造方案）。
- 可观测：结构化事件、首页系统状态、归因链。

### 1.3 本阶段不做（Out of Scope）

- 多租户商业化、计费与 SLA。
- 每产品一套 Agent 实例（共享班组策略）。
- 新增非现有渠道的发布能力。
- 深度定制 AgentTeams 源码。
- 移动端与多端适配。

## 二、核心领域模型

### 2.1 名词表

| 名词 | 定义 |
|---|---|
| 产品（Product） | 推广对象，用户维护的业务配置核心 |
| 产品资料快照（SourceSnapshot） | 上传资料的版本化快照，随更新重建 |
| GEO 蓝图（GeoBlueprint） | 已批准调研结论（问题、渠道、边界） |
| 产品策略包（StrategyPack） | 编译产物，绑定蓝图 + 资料快照 + 规则版本，只读默认、高级调整二级入口 |
| 生产任务 / 排程任务 / 发布记录 | 主链路任务对象，均带幂等键与责任字段 |
| 责任状态（Responsibility） | `system / external / user` |
| 恢复状态（RecoveryStatus） | `waiting / retrying / repaired / exhausted` |
| 采集设备（CaptureDevice） | 绑定 `workspaceId + userId + deviceId`，可撤销 |
| 采集任务（CaptureTask） | 问题 × 平台 × 设备，Lease + 心跳 + 幂等键 |
| 证据工件（EvidenceArtifact） | 脱敏回答 + 引用 + 截图 + SHA-256，不可变、可版本化 |
| 归因链（AttributionChain） | 表现下降 → 平台变化 → 证据 → 策略调整 → 文章 → 效果恢复 |

### 2.2 产品状态机

`待调研 → 调研中 → 策略就绪 → 生产中 → 铺设中 → 监控中 → 迭代中 → 需介入 / 暂停`

迁移条件：

- 资料快照满足完整度阈值 → 自动进入调研。
- 调研结果编译通过 schema 校验 → 策略就绪（重大变化需用户确认后生效）。
- 策略就绪 → 自动生产。
- 生产质检通过 → 自动排程发布。
- 发布回传 + 存活验证 → 监控中。
- 缺口识别在批准边界内 → 自动回迭代调整；超边界 → 需介入。

### 2.3 统一责任模型

| 状态 | 含义 | 用户是否操作 |
|---|---|---|
| 系统运行中 | 正常生成、排程、发布、核验 | 否 |
| 系统处理中 | 已发现异常，正在重试、修复或顺延 | 否 |
| 等待外部结果 | 等待平台审核、URL 回传、24h/72h 验证 | 否 |
| 需你处理 | 系统确认无法自行恢复 | 是 |

任务统一字段：`responsibility`、`recoveryStatus`、`nextAutomaticAction`、`nextAttemptAt`、`attemptCount`、`impactCount`、`userActionRequired`。

## 四、功能需求

### 4.1 上传与授权

- 用户上传产品资料，系统自动解析、去重、入库并生成资料快照。
- 用户连接发布账号（每个账号配置保守日上限、可发布时段、最小间隔）。
- 用户安装/配对采集设备，一次性配对码短期过期，设备可撤销。
- 授权完成后，产品进入自动运行状态。

### 4.2 调研与策略编译

- 系统自动执行 GEO 调研（问题池、关键词池、竞品），无需用户选择问题集合。
- 调研结果 + 资料快照 + 规则包编译为产品策略包，schema 校验通过后生效。
- 策略包记录：重点问题、内容类型、渠道、数量及原因、蓝图版本、资料版本、更新时间。

### 4.3 生产与质检

- 按策略包自动创建生产任务并生成正文（后台任务，用户关页不中断）。
- 质检门：证据对齐、CTA、格式；失败自动修复并重新质检。
- 防重复：相同"问题 + 内容类型 + 渠道"在冷却期内不重复生成。

### 4.4 发布与排程

- 排程读取账号日上限与已有占用；达到上限自动顺延到下一可用时段/日期。
- 月末溢出任务进入下一月执行快照，不丢失、不要求用户重建。
- 发布成功自动回传 URL；网络/超时自动重试；资料不足、账号失效、风控进入异常区。

### 4.5 监控与采集

- 自动执行公开校验、24h/72h 存活检查。
- 系统自动生成"问题 × 平台"采集矩阵并分配设备；设备离线自动转移任务。
- 采集结果脱敏、哈希校验后进入 GEO 基线；不合格自动重采或升级。

### 4.6 迭代与报告

- 快速闭环：缺口 → 边界内自动调整优先级与数量 → 补充生产。
- 治理闭环：定位/事实/合规变化 → 生成新版蓝图候选 → 用户确认 → 更新边界。
- 月度报告由系统自动生成（结果 + 归因 + 下月建议），用户不再手工创建 Proposal。

### 4.7 需你处理

- 仅四类：账号失效/封禁/验证码、设备全失效、事实与合规冲突、连续自动修复达上限。
- 每条告警展示四要素：发生了什么、影响什么、系统下一步做什么、预计何时再次检查。

## 五、接口与 MCP 契约

### 5.1 关键 API（新增/改造）

| 方法 | 路径 | 用途 |
|---|---|---|
| PUT | `/api/v5/products/:id/promotion` | 开始/暂停推广 |
| POST | `/api/v5/products/:id/source-snapshot` | 触发资料快照重建 |
| GET | `/api/v5/products/:id/strategy-pack` | 查看策略包（只读） |
| POST | `/api/v5/products/:id/strategy-pack/apply` | 应用策略包（含审批） |
| GET | `/api/v5/tasks/responsibility` | 按责任状态聚合任务 |
| GET | `/api/v5/tasks/attention` | 需你处理清单 |
| POST | `/api/v5/capture-devices/*` | 设备配对/撤销/心跳 |
| POST | `/api/v5/capture-tasks` | 创建采集任务矩阵 |
| POST | `/api/v5/capture-tasks/:id/lease` | 领取/续租任务 |
| POST | `/api/v5/capture-evidence` | 上传脱敏证据（幂等） |
| POST | `/api/v5/attribution` | 写入归因链事件 |

### 5.2 MCP Server 清单

| Server | 暴露能力 | 对应 API |
|---|---|---|
| 知识库 MCP | 采集/治理/检索 | `/api/v5/knowledge-*` |
| GEO 调研 MCP | 问题池/关键词池/调研 | `/api/v5/questions`、`/api/v5/semantic-keywords` |
| RAG 检索 MCP | 向量+关键词检索/证据对齐 | `/api/rag/retrieve`、`/api/rag/evidence-packs` |
| 发布 MCP（已有） | 排程/发布/回传/重试 | publish-mcp-server |
| 复盘观测 MCP | 存活验证/数据回传/复盘 | observation + publish-records API |
| 采集任务 MCP | 设备配对/任务分发/租约/工件 | `/api/v5/capture-*` |

## 六、非功能需求

| 类别 | 要求 |
|---|---|
| 稳定性 | 热路径不经过 LLM/Matrix；阶段质量门；编排层故障可旁路 |
| 幂等 | 发布、采集、证据上传均携带幂等键；断线从数据库恢复 |
| 成本 | 阶段间传递结构化快照而非原始上下文；共享 Worker 班组；LLM 调用有预算上限 |
| 安全 | Worker 不持真实凭证（Higress consumer token）；采集不搬登录态、不上传 Cookie/Token；设备凭证可撤销 |
| 可观测 | 每阶段产出结构化事件（阶段、耗时、token 成本、结果、归因链）；AgentTeams heartbeat 并入责任模型 |
| 性能 | 单产品策略包编译 < 1 分钟；发布排程决策 < 10 秒；页面 15 秒自动刷新不阻塞 |

## 八、里程碑与验收标准

### Phase 0：确定性闭环（约 2 周，不依赖 AgentTeams）

- [ ] 上传资料 → 调研 → 策略包编译 → 后台正文生成 → 容量排程 → 发布回传，全链路无人值守可跑通
- [ ] 责任判定器上线：首页/当日执行/发布监控不再把 `system_recovering` 等计入"需处理"
- [ ] 月末溢出任务进入下一月执行快照
- [ ] 验收：跑通 1 个真实产品（如腾讯云 ADP）全链路，无人工介入完成发布与回传

### Phase 1：MCP 契约化（约 2 周）

- [ ] 6 个 MCP Server 可用，契约文档齐备
- [ ] capture-devices 落地：设备配对/撤销/心跳/Lease/证据上传
- [ ] 验收：通过 MCP 客户端调用知识库、调研、发布能力成功

### Phase 2：AgentTeams 接入（约 3 周）

- [ ] Docker 本地跑通 Manager + 职能 Workers
- [ ] Human 映射采集执行人；Matrix 通知接入"需你处理"
- [ ] 编排层故障可旁路（降级演练通过）
- [ ] 验收：Manager 分派任务 → Worker 调 MCP → 结果回房间 → 房间消息进入审计

### Phase 3：迭代闭环（约 3 周）

- [ ] 缺口自动识别并在边界内调整策略包
- [ ] 效果归因链完整落库并展示
- [ ] 月度报告自动生成
- [ ] 验收：连续 2 个观测周期自动迭代，无人工干预次数占比 > 90%

## 九、风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| LLM 编排进入热路径 | 抖动、成本、停滞 | 热路径确定性边界 |
| Matrix 消息丢序/延迟 | 任务流转错乱 | 状态以数据库为准，Matrix 仅通知与审计 |
| AgentTeams 版本能力差异 | 文档能力与实现不符 | 先本地 PoC 验证再铺开 |
| 采集依赖真人 | 无人在线时闭环中断 | 自动化渠道优先，真人仅兜底 |
| 多产品上下文串扰 | 策略污染 | 产品快照隔离 + schema 校验 |
