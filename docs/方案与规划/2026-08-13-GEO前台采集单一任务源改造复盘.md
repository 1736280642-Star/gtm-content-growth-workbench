# GEO 前台采集单一任务源改造复盘

## 结论

正式 AI 前台测试现在以 MySQL `capture_tasks` 为唯一任务源。策略编译只保存复测规则，不再提前创建任务；正式内容发布成功后，系统才按发布内容和平台幂等创建复测任务。

## 实现逻辑

1. `content_publish_result` 写入 `published` 时，在同一数据库事务中创建 `published_content_retest` 任务，并记录 `questionVersionId`、`publishedContentId` 和 `sourcePublishResultId`。
2. 本机 Runner 通过设备注册和心跳保持在线，从 MySQL 队列领取任务租约，再把任务交给豆包、DeepSeek、千问、ChatGPT 四平台浏览器适配器执行。
3. 浏览器伴侣回传的脱敏结果统一为 `frontend-capture-evidence.v1`，服务端转换为 `CapturedAnswer`、`Citation` 和候选 `Gap`；原始证据按哈希保持不可变，人工复核写入独立表。
4. AI 前台测试页、MonthlyReview 和 GEO 监控均通过正式 Capture Repository 聚合 MySQL 数据。JSON Observation 仅保留为无正式数据库的测试 fixture，不参与正式聚合。

## 底层原因与用户影响

- 单一任务源消除了 JSON 状态和 MySQL 队列互相不可见的问题。
- 发布结果与复测任务直接关联，GEO 监控展示的是文章发布后的真实变化，而不是策略阶段的预测任务。
- 租约、设备心跳和证据哈希分别解决重复执行、离线设备占用和结果篡改问题。
- Chrome 浏览器伴侣仍是实际操作 AI 前台的必要执行端；Runner 不模拟登录、不绕过验证，也不上传 Cookie、密码或 Token。

## 验收与后续

先连续完成 3 次“正式发布 → 自动建任务 → 设备租约 → 真实采集 → MonthlyReview 可见”的运行验收。达到后再把设备排障、Adapter 校验和证据验收步骤沉淀为统一 Capture Skill/SOP；在此之前不把未验证流程固化为自动化资产。
