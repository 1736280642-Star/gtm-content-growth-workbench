# Phase 2A 产品 GEO 策略门禁开发成果与验收报告

> 日期：2026-08-10  
> 对应基线：《2026-08-10-不接AgentTeams-GEO产品闭环多阶段开发方案指南》  
> 阶段结论：Phase 2A 工程能力通过；WorkBuddy 真实策略内容仍需 Phase 2B 调研结果后生成。

## 1. 结论

产品级人工判断已经从 GeoBlueprint 收敛到唯一的“产品 GEO 策略”入口：

```text
系统完成内部调研综合
→ 编译 pending_strategy_review 策略
→ 用户在产品页确认或拒绝
→ 确认后才写入产品当前策略
→ 样稿通过前不进入自动批量生产
```

系统、Scheduler 和 Agent 不能再自动批准调研综合稿或产品策略。拒绝新策略不会清空旧的已确认策略。

## 2. 实现逻辑、底层原因与用户影响

| 改动 | 实现逻辑 | 底层原因 | 用户影响 |
|---|---|---|---|
| 策略状态机 | 编译只生成 `pending_strategy_review`；人工确认后进入 `strategy_approved` | 编译是机器动作，不能等价于人工判断 | 用户确认前，系统不会偷偷切换策略 |
| Human 门禁 | 检查 actor type、角色、expectedVersion、幂等键和审计原因 | 正式域禁止 Agent 创建人工批准 | 操作人和修改原因可追溯，重复点击不重复生效 |
| 旧策略保护 | 拒绝新草稿时只处理新草稿；旧 current strategy 保留 | 新提案失败不应导致生产真相丢失 | 用户可以安全拒绝错误策略 |
| 稳定版本顺序 | 新增产品级 `strategy_version`，编译时锁产品行后分配版本 | `DATETIME` 秒级排序不能区分同秒编译 | “最新策略”稳定，不会随机回退 |
| GeoBlueprint 内部化 | 去掉研究页批准/退回操作和用户可见蓝图措辞 | 蓝图是内部综合中间物，不应增加认知负担 | 用户只看最终策略、依据和高级信息 |
| 统一产品入口 | 产品详情新增“GEO 策略”页签，展示定位、问题、类型、证据和确认按钮 | 策略判断必须发生在信息完整的同一上下文 | 无需在调研页、类型页和月度页来回切换 |
| 生产保护 | Capture 只修改产品当前且 `production_ready/legacy active` 的策略 | 策略确认不代表样稿质量已通过 | Phase 2D 样稿验收前不会误进入生产 |

## 4. 验收证据

### 4.1 数据库迁移

```text

```

019 建立策略人工决策字段、乐观并发和幂等字段；020 建立稳定的产品级策略版本号。

### 4.2 领域单元测试

```text
test:v5-product-strategy: 4/4 passed
```

覆盖：V2 编译、Human/角色限制、状态转换、禁止自动批准、研究页无蓝图审批。

### 4.3 真实 MySQL 集成测试

```text
test:v5-product-strategy:integration: 1/1 passed
```

一个集成场景完整证明：

1. 系统编译后状态是待确认，产品 current strategy 为空。
2. System actor 批准被拒绝。
3. Human actor 批准成功并更新 current strategy。
4. 同一幂等键重放不增加版本或重复副作用。
5. 新策略生成后，旧 current strategy 继续保留。
6. 拒绝新策略后，旧 current strategy 仍然保留。
