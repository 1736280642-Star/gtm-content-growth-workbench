# Phase 2G MonthlyReview 证据门禁开发进展报告

日期：2026-08-10（2026-08-12 更新）

## 结论

MonthlyReview 的工程证据边界已补齐，但 Phase 2G 需要至少两个真实月度观察周期，当前不能宣称完成。

## 修改

- 正式适配器继续只读取 `content_publish_result.status='published'` 的发布结果。
- 无正式发布内容的问题不能生成下月调整 Proposal。
- Proposal 新增不可解释结论所需的证据引用：`published_content:*`、`geo_capture_task:*`、`confirmed_gap:*`。
- 正式发布结果新增 `publishScheduleId`、首次公开时间、最后验证时间、稳定时间、移除时间和验证次数；24h/72h 状态进入 MonthlyReview。
- 文章发布后被删除时，系统保留“曾正式发布”的事实，并把删除作为存活失败记录，不再覆盖成“从未发布成功”。
- 下月 Proposal 冻结 `publish_liveness_24h:*`、`publish_liveness_72h:*` 引用；正式数据未完成 72 小时观察时拒绝提前形成调整 Proposal。
- “有效回传”只统计真实平台指标，不把“待观察”的存活状态误算成指标回传。
- 旧 Proposal 读取时兼容缺失的 `evidenceRefs`，不会破坏历史数据。
- 计划数可以用于展示完成率，但不能单独成为效果结论或下月变更依据。

## 用户影响

用户看到的下月建议能够追溯到真实发布、GEO 复测和已确认缺口；系统不会因为“本月计划过某篇内容”就推断其有效，也不会自动改变重大产品策略。

当前 MySQL 已应用 `20260812_028_v5_publish_observation_lifecycle.sql`，7 个生命周期字段全部验证存在；真实 MySQL 集成测试证明同一发布任务的后续存活验证只更新原结果，不重复创建发布记录。

## 后续真实验收

- Phase 2F 产生真实公共 URL、24/72 小时状态和平台指标。
- GEO 复测与对应发布内容建立关联。
- 连续两个 `MonthlyReview` 仅基于正式数据生成提案，并由人确认重大策略变化。
